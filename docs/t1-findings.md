## 🔴 2 回目: 検知は発火したが、送信元を取り違えた (2026-08-05)

文言パターンを直した版で、**検知・投稿・固定まで一通り走った。**ただし
**送信元が「配信者自身のチャンネル」になっていた。**

```
[yt-redirect-pin] 投稿する (auto): @<配信者自身>さんからリダイレクトありがとうございます! ...
[yt-redirect-pin] 起動した {build: ..., enabled: true, debug: false, pinMode: 'ifEmpty', cooldownSec: 600}
[yt-redirect-pin] クールダウン中のためスキップ ...
[yt-redirect-pin] 既に固定中のメッセージがあるため固定しない (pinMode=ifEmpty)
[yt-redirect-pin] 固定結果: skipped
```

### 原因

**`投稿する` が `起動した` より前に出ている**のが決め手。起動時の既存ノード走査
(`scanExisting`)が**チャット項目リスト全体を 1 つの要素として**渡していた。

`collectRedirectNotices` は外側から順に見て最初に一致した要素を通知としていたため、

1. リスト全体のテキストに「とその視聴者が参加しました」が含まれる → **リスト全体が一致**
2. `extractHandleFromText` がリスト全体のテキストから**最初の `@ハンドル`** を拾う
3. それはリダイレクト送信元ではなく、チャット内の無関係なハンドルだった

外側から見て最初の一致を採る限り、この誤りは必ず起きる。

### 直した点

1. **子孫を先に見て、最も内側で一致した要素を通知とみなす。**
2. **テキスト長の上限 (300 文字) を通知の条件に加えた。**チャット欄やリスト全体のような
   長いテキストの塊は通知ではない。
3. 回帰テストを追加(リスト全体を渡しても、リスト内の別のハンドルを送信元にしない)。

### この回で確認できたこと

- ✅ **文言パターンは正しい。**「とその視聴者が参加しました」で検知が発火した
- ✅ **投稿が実際に成立した。**チャット入力欄への入力と送信が通った (T5 の経路が動く)
- ✅ **`ifEmpty` が「固定あり」を検出して skipped を返した。**hidden な placeholder との
  区別ができている(ただし本当に何か固定されていたかは要確認)

### 固定できなかった原因は「開き方」だった

`click()` だけでは Polymer のドロップダウンが開かない。効いたのは:

1. **イベントに座標(要素の中心)を入れる。** 座標 0,0 のイベントを無視する実装がある。これが本命
2. `buttons` / `detail` を人の操作に合わせる
3. 内側の `button` とホスト (`yt-icon-button`) を**順に**試す(同時に流すと開いた直後に閉じる)
4. メニュー項目はサーバから取りに行くため、待ちを 2s → 4s に延ばす

この経路が無かったため、原因特定に実配信の往復を何度も使ってしまった。

## 🔴 2026-08-06: 実害のある誤動作 4 件

### 1. 他人の配信のチャットへ投稿していた

content script が `www.youtube.com/live_chat*` にも注入されるため、**他人の配信のチャットを
開いているだけで動いた。**その配信がリダイレクトを受けると自分の名義で投稿してしまう。

→ **`studio.youtube.com` のライブ管制室だけを対象にした**(manifest ごと。設定で許可する
余地も持たせない)。管制室は自分の配信でしか開けないため、「自分の配信である」ことの
代わりに使える唯一の確実な手掛かり。

### 2. リダイレクトを「送った」側のバナーに反応していた

送信側にもバナーが出る: `この機会に、@<送信先> のコンテンツの視聴を促進しましょう`。
**そこに載っているのは送信先であって送信元ではない**ため、自分が送った相手に
「ありがとうございます」を投稿する逆向きの誤動作になる。

原因は、推測で置いた `[class*="redirect"]` 等のセレクタが**文言チェックを飛ばす経路**
だったこと。この文言は通知の文言パターンのどれにも当たらないので、**推測セレクタを
削除しただけで解消した**(除外パターンは保険)。

> **教訓: 未確認の推測を、チェックを飛ばす強い経路に置かない。**
> `TODO(T1)` は付けていたが、危険度に見合った扱いをしていなかった。

### 3. `decodeURIComponent` の例外でパイプラインが落ちた

日本語ハンドル対応で入れた `decodeURIComponent` が、壊れたパーセントエンコード
(単独の `%` 等)で `URIError` を投げ、検知はできているのに投稿されない状態になった。
デコードは見栄えの処理なので失敗しても困らない。握って元の文字列を返すようにした。

### 4. チャットを再読み込みすると、同じ相手へ何度も投稿していた

**報告 (2026-08-06):** ブラウザを再読み込みすると、リダイレクトのバナー(通知)がチャットに
残ったままなので、**それに反応して複数回投稿されることがある。**

原因は 2 つが重なったもの:

- 通知は**一度出たら消えない。**リロード後の初期走査 (`detector.scanExisting`) が、残っている
  通知を「新しい通知」として拾い直す。**これは仕様どおりの動作**(リロード後は observer の
  追加イベントが来ないため、初期走査が唯一の検知経路)。
- 抑止 (`dedupe`) の記録が**メモリ上にしか無かった。**「同一配信内」を「チャット文書の
  ライフサイクル」で代用していたため、**リロードのたびに抑止が白紙に戻っていた。**
  ノード単位の抑止 (`WeakSet`) も同じ理由で消える。

→ **投稿できたときだけ「誰に・何を・いつ・どの配信で」を `chrome.storage.local` に残し、
起動時に読み戻して抑止の初期値にする** ([src/post-log.ts](../src/post-log.ts))。

**クールダウンの適用範囲は「同じ配信の中」だけ** (2026-08-07 に方針決定):

- **配信が違えば、クールダウンに関係なく投稿する。**別の配信で受けたリダイレクトは別の出来事。
  読み戻すのも**今の配信の記録だけ**にする。
- 同じ配信の中は、設定のクールダウン秒数で判定する。
- ⚠️ **通知は消えずに残るので、秒数が短いと開き直すたびに再投稿しうる。**
  UI とドキュメントで「配信の長さ以上」を目安として案内している。
- クールダウン `0`(抑止なし)は従来どおり通す。同じ相手で繰り返し試すための逃げ道。
- 配信 ID は **① 自分の URL の `v=`(ポップアウト)→ ② 親フレームの管制室 URL
  (`/video/<id>/livestreaming`)** の順に探す。
  ✅ **実配信で確認 (2026-08-07)。管制室の埋め込みチャットのフレーム URL は
  `/live_chat?continuation=...` で `v=` を持たない。**②の親フレーム経由でのみ取れる
  (同一オリジンなので読める)。①だけの実装では、この画面で配信を特定できない。
- それでも取れないときは「同じ配信か」を判定できないので、**保存済み履歴に対してだけ
  クールダウンの下限を 6 時間**にして安全側へ倒す。同じ画面のままの連続発火は、
  設定どおりの秒数で判定する(設定の意味を変えないため)。

## 🔴 2026-08-07: 固定済みのメッセージを `unavailable` と誤報していた

**報告:** `メニューに「固定」項目が見つからない` の警告が、**既に固定されているときに出ている**。

そのとおりだった。**固定済みのメッセージのメニューには「メッセージを固定」が無く、
「固定を解除」が出る。**`findPinMenuItem` は取り違え防止のため「固定を解除」を除外して
いたので、固定済みの相手では必ず空振りし、メニューの待ちを 2 系統ぶん(最大 8 秒)使ったうえで
`unavailable` を警告していた。

```
メニューに「固定」項目が見つからない {popupCount: 3, popups: Array(3), roleMenuItems: Array(3)}
固定結果: unavailable
```

> 3 項目並んでいるのに「固定」が無い、が手掛かりだった。`["チャンネルへ", "固定を解除", "削除"]`。

→ **「固定を解除」があること自体を「そのメッセージは固定されている」証拠として扱う。**
待ちは「固定」か「固定を解除」のどちらかが出るまでに変え、後者なら**メニューを閉じて
`pinned` を返す**(解除は押さない)。目的の状態(このメッセージが固定されている)は
既に満たされているため。

### ただし実際に出ていた警告の原因は別だった

上記を直しても警告が消えず、`roleMenuItems` を展開して判明した:

```
roleMenuItems: ['Q&A を開始 視聴者の質問にライブで回答します',
                'アンケートを開始 視聴者の意見を聞いてみてます', '閉じる']
```

**これはメッセージのメニューではなく、チャットの「Q&A / アンケート」メニュー。**しかも
**閉じている。**つまり「メッセージのメニューが開いていない」のに、**別の閉じたドロップダウンの
中身を読んで「固定項目が無い」と報告していた。**

- このドロップダウンは**閉じていても DOM に常駐し、`aria-hidden="true"` が付かない。**
  セレクタ側の `:not([aria-hidden="true"])` では除外できない。
- **要素自身の `display` を見るだけでは足りない。**`display:none` の親の中にいる子要素は
  `getComputedStyle(子).display` が `none` にならない(継承される値ではない)。
  → **祖先までさかのぼって**表示を確認する (`isDisplayedDeep`)。

→ `getOpenMenuItems` を「実際に表示されている項目だけ」に変更。あわせて診断ログに
`openMenuItems` を足し、**「メニューが開かなかった」と「開いたが固定が無い」を言い分ける**
ようにした。前者では警告文自体を変える。

### これは警告の誤報だけでなく、固定が通らない原因そのものだった

`queryAll` は候補セレクタを順に試し、**最初に 1 件でも当たった候補を採用する。**閉じた
Q&A メニューの項目が最初の候補に当たっていたため、**実際に開いたメッセージのメニューの項目は
一度も見られていなかった。**表示状態で絞ったことで本物のメニューが見えるようになり、
**✅ 自動経路の通し(検知 → 投稿 → その投稿を固定)が実配信で通ることを確認 (2026-08-07)。**

> **教訓: 「見つからない」を報告するときは、探した場所が正しいかを同時に示す。**
> 誤った場所の中身を根拠に「無い」と言うと、原因の切り分けが 1 往復では終わらない。
> **「最初に当たった候補を採る」フォールバックは、当たり方が間違っていると後続を全部隠す。**
- 設定ページに **「投稿履歴」**(一覧 + 履歴を消す)を追加した。抑止された根拠が人から見え、
  同じ配信でもう一度投稿したいときの手段にもなる。

**✅ 解消を実配信で確認 (2026-08-07)。**リロードしても再投稿しなくなり、`streamId` も取れている。
なお**旧ビルドのまま検証して「直っていない」と 2 往復した。**`起動した` の `build` を最初に見ること
(このために起動ログへ載せてある)。

> **教訓: 「文書のライフサイクル = 1 配信」は成り立たない。**リロードでも
> ポップアウトの開き直しでも文書は作り直される。**画面の状態(残っている通知)を
> 入力にしている以上、抑止の記録は画面より長生きしなければならない。**
