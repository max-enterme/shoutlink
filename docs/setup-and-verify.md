## 1. ビルド

```bash
npm install
```

```bash
npm run build
```

`dist/` に拡張の実体(`manifest.json` / `content.js` / `options.html` / `options.js`)が出る。
`dist/` は `.gitignore` 済みで、コミットされない。

テストを流すなら:

```bash
npm run typecheck && npx vitest run
```

## 2. Chrome へ読み込む

配信で使っている Chrome(ログイン済みのプロファイル)で行う。

1. `chrome://extensions` を開く
2. 右上の **デベロッパーモード** を ON
3. **「パッケージ化されていない拡張機能を読み込む」** → このリポジトリの `dist/` を選ぶ
4. カードに **「返礼リンク」** が出れば読み込み完了

**コードを直したら `npm run build` → `chrome://extensions` のカードの ⟳(更新)を押す。**
押し忘れると古いコードが動き続ける。

## 3. 設定

`chrome://extensions` の「返礼リンク」 → **詳細** → **拡張機能のオプション**(別タブで開く)。

| 項目 | 内容 | 既定 |
|---|---|---|
| リダイレクトを自動検知して投稿する | OFF にすると**リダイレクト返礼の自動投稿だけ**が止まる。手動トリガーは通る (001 AC7)。**コメント返しはこのスイッチでは止まらない** | ON |
| 投稿文テンプレート | `{name}` = 送信元の表示名 / `{url}` = チャンネル URL (001 AC5) / `{msg}` = **リダイレクト返礼用**の自由文。下にプレビューが出る | `{name}さんからリダイレクトありがとうございます! {url}` |
| コメントに反応して投稿する | 辞書で「コメントに反応する」を付けた人のコメントに反応する (004 AC1)。**OFF の間は検知そのものを走らせない** | **OFF** |
| コメント返しの文面 | **リダイレクト返礼とは別のテンプレート** (004 AC5)。`{name}` `{url}` は**辞書側の値だけ**を使い、**コメント側の表示名は使わない**。`{msg}` = **コメント返し用**の自由文(`commentMessage`。003 の `message` は入らない / AC16) | `{name}さん、来てくれてありがとうございます! {url}` |
| 固定モード | `off` 固定しない / `ifEmpty` 既存の固定が無いときだけ / `always` 上書き (AC8) | `ifEmpty` |
| クールダウン | 同一送信元からの再投稿を抑止する秒数。**同じ配信の中でだけ効く。**0 で抑止なし (AC4) | 21600 秒(6 時間) |
| 投稿履歴 | 投稿できた「誰に・何を・いつ」の記録(この端末のみ / 同期しない)。消すと同じ相手にもう一度投稿できる | — |
| 投稿履歴の**種別**列 | `リダイレクト返礼` / `コメント返し`。抑止が**非対称**なので種別で分けて記録する (004 AC8) | — |
| 呼び名の辞書 | `{name}` を置き換える呼び名と、`{msg}` に入る自由文 2 本(どちらも 1 件 200 字まで)。**この端末のみ / 同期しない**。**行は畳んである** — 左端の `▸` で 自由文 2 本 + 「コメントに反応する」が開く (004 AC13 / T14 の確定) | — |
| 辞書の「コメントに反応する」 | 行ごとのフラグ。**ON にした時点でその行の `channelId`(`UC…`)を取りに行く**(004 AC17)。**未解決の行はコメント照合の対象外**で、畳んだ状態でも ⚠ が出る | **false**(自動登録でも false) |
| 手動トリガーを出す | ライブチャット右下の「↩ 返礼」。**チャット窓を配信画面に載せていると映り込む**ため既定 OFF | OFF |
| 診断ログ | 通知の候補になりうるノードをコンソールに出す | OFF |

> **クールダウンは「同じ配信の中」でだけ効く。**判定は投稿履歴に基づき、**リロードしても
> 引き継がれる**(2026-08-06 の不具合。通知はチャットに残り続けるので、記録が消えると
> 開き直すたびに再投稿する)。
>
> - **配信が違えば、クールダウンに関係なく投稿する。**別の配信で受けたリダイレクトは別の出来事。
> - 同じ配信で同じ相手にすぐ投稿させたいときは、**投稿履歴を消す**か、クールダウンを `0` にする。
> - ⚠️ **同じ配信でも、クールダウンが明ければ再び投稿する。**通知は消えずに残るため、
>   秒数を短くすると「開き直すたびに投稿」が起きうる。**配信の長さ以上**を目安にする
>   (例: 6 時間 = `21600`)。

> クールダウンを `0` にしても、**自分が投稿した直後 30 秒は同じ相手の自動検知を止める**
> (固定バナー経由の自己ループ抑止 / security-review.md S1)。手動トリガーはこの抑止を受けない。

> **呼び名の辞書の保存先は `chrome.storage.sync` → `chrome.storage.local` に移した**
> (003 / security-review.md S7)。`sync` は 1 アイテム 8KB 上限で、辞書は配列まるごと 1 アイテム。
> 自由文が加わると数十件で頭打ちになり、超えると `set` が reject して `guardAsync` が握るため
> **コンソールに 1 行出るだけで以後の登録が保存されない**。
>
> - **代償: 端末間で同期されなくなる**(配信は 1 台で回す前提。投稿履歴と同じ判断)
> - `sync` からの引き継ぎは **`local` にキーが無いときだけ / 1 度きり**。走るのは `loadDirectory`
>   の中なので、**チャットと設定ページのどちらから開いても同じログが 1 行出る**
>   (`呼び名辞書を chrome.storage.local へ引き継いだ: N 件 (理由)` / `呼び名辞書の引き継ぎはしていない: 理由`)。
>   **辞書の書き込みに失敗したときは警告が出て、次回に再試行する**(移行済みフラグは立てない)。
>   辞書は書けてフラグだけ書けなかった場合は `migrated` 扱い — 次回は「既に local に辞書がある」で
>   止まるので、再試行は起きないし要らない
> - **`sync` 側のキーは消さない**(片方向コピー)。消すと、まだ移行していない別 PC から辞書が消える

> **`always` は既存の固定(告知など)を消す。**YouTube の固定は 1 件のみ。
> `ifEmpty` は「現在何かが固定されているか」の DOM 判定に依存しており、これは未検証 —
> 判定用セレクタが外れていると、**`ifEmpty` が実質 `always` として振る舞う**(既存の固定を消す)。
> 告知を固定して配信するなら、当面は `off` が安全。

## 4. 動く場所

content script が注入されるのは **Studio のライブ管制室のチャットだけ**:

- `https://studio.youtube.com/live_chat*` — 管制室の埋め込みチャットと、そこからのポップアウト

**`https://www.youtube.com/live_chat*` は意図的に対象外**(2026-08-06 の事故 / plan.md「対象ウィンドウ」)。
`www` のライブチャットは**他人の配信でも開ける**ため、そこで動かすと他人の配信のチャットへ
自分の名義で投稿しうる。`manifest.json` の `matches` から外したうえで、`src/scope.ts` でも
ホスト名を見て二重に止めている。設定で `www` を許可する経路は無い。

> ⚠️ **`host_permissions` には `https://www.youtube.com/*` が入っている(004 / AC17)。
> 注入範囲とは別物。**
>
> | | 注入 (`content_scripts.matches`) | 取得 (`host_permissions`) |
> |---|---|---|
> | 範囲 | `https://studio.youtube.com/live_chat*` **のみ**(004 で 1 つも増えていない) | `studio.youtube.com/*` と **`www.youtube.com/*`** |
> | 何に使う | 検知・投稿・固定 | **設定画面から**チャンネルページを取得して `UC…` を控える([channel-id.ts](../src/channel-id.ts)) |
> | いつ | そのページを開いている間 | 人が「コメントに反応する」を ON にした / 再試行を押したときだけ |
> | チャット画面では | 動く | **通信しない** |
>
> **注入範囲は [tests/manifest.test.ts](../tests/manifest.test.ts) で機械的に固定してある**
> (事故 1 の再発防止が文書と `scope.ts` だけだったため / security-review.md S10)。
> 利用者から見えるのは**インストール時の許可表示が 1 つ増える**ことなので、
> README / install.md / index.html / for-testers.md / privacy-policy.md と
> **配布 ZIP の `INSTALL.txt`** に説明を入れてある。

ポップアウトの開き方: 管制室のチャット右上の **⋮ → チャットをポップアウト**。
独立ウィンドウになるので、サブモニタに小さく置いておける
(URL が `studio.youtube.com/live_chat?is_popout=1&v=...` になっていることを確認する)。

読み込めているかはコンソールの `[shoutlink] 起動した {...}` で判る。出ていなければ
注入されていない(URL が `studio.youtube.com/live_chat` か、拡張が有効か、⟳ を押したかを確認する)。

設定で **「手動トリガーを出す」を ON** にすると、チャット画面の右下に **「↩ 返礼」** が出る
(既定は OFF)。切り替えにページの再読み込みは要らない。

## 5. 動作確認

### 事前に

- **本番配信でいきなり試さない。** 自分の限定公開 or 非公開のテスト配信を立てて、そこでやる。
  投稿は実際にチャットへ流れる。
- ログは DevTools のコンソールに `[shoutlink]` 付きで出る。
  - ポップアウトチャットは**独立ウィンドウ**なので、そのウィンドウで F12 を押す。
  - watch ページ埋め込みで見る場合は、コンソール左上の**フレーム選択**を `live_chat` に切り替える。

### A. 手動トリガーでの通し確認(リダイレクトを受けなくてもできる)

**これが一番先にやるべき確認。**投稿 → 固定の経路(②③)を、自動検知(①)と切り離して確かめられる。

1. テスト配信のライブチャットを開く(ポップアウト推奨)
2. オプションで「リダイレクトを自動検知して投稿する」と **「ライブチャットの右下に「↩ 返礼」を出す」** を ON にする
3. 右下の **「↩ 返礼」** をクリック
4. 「送信元チャンネル URL / @ハンドル」に、適当なチャンネル URL(自分のサブチャンネル等)を入れる
5. 「表示名」は空でよい(空なら URL のハンドルで埋まる)
6. **「投稿して固定」** を押す

期待する結果:

| 見るところ | 期待 |
|---|---|
| チャット | テンプレートどおりの文面が投稿される (AC2) |
| チャット上部 | 固定モードに従って固定される (AC3 / AC8) |
| コンソール | `投稿する (manual): ...` → `固定結果: pinned` |

もう一度同じ URL で押すと `クールダウン中のためスキップ`(前回の文面と時刻付き)が出て
投稿されない (AC4)。別の URL なら通る。**この抑止はページを再読み込みしても残る。**
繰り返し試すときは、オプションの**投稿履歴を消す**か、クールダウンを `0` にする。

### B. 固定モードの確認 (AC8)

`off` / `ifEmpty` / `always` を切り替えて、A を繰り返す(クールダウンを 0 にするか、毎回違う URL を使う)。

| モード | 既存の固定なし | 既存の固定あり |
|---|---|---|
| `off` | 投稿のみ・固定しない | 投稿のみ・固定しない |
| `ifEmpty` | 固定される | **既存の固定が残る**・投稿だけされる |
| `always` | 固定される | **既存の固定を上書きする** |

コンソールの `固定結果:` が `pinned` / `skipped` / `unavailable` のどれになるかで判定できる。
`unavailable` = 固定 UI が見つからなかった(投稿は成立している / AC6)。

### C. 自動検知の確認 (T1 / T1b 相当)

**実際に他チャンネルからリダイレクトを受ける必要がある。**送る側には登録者 1,000 人以上の要件があるが、
受ける側には無い。受け取り許可の既定は「登録しているチャンネル」なので、テスト相手のチャンネルを
登録しておく必要がある(spec.md 制約)。

リダイレクトを受けたら:

1. コンソールに `投稿する (auto): ...` が出るか
2. 出ない場合 → **通知ノードが検出できていない。**下の「切り分け」へ
3. 出た場合 → 受信から投稿まで 10 秒以内か (AC1)

あわせて T1b の確認:

- ポップアウトチャット単独で通知が出るか(管制室の画面上にしか出ないなら、
  ポップアウトだけでは検知できない / plan.md C1)
- 埋め込みとポップアウトの両方で「固定」メニューが出るか (C2)
- **チャットウィンドウを最小化 / 非前面にした状態でも発火するか** (C3)

### C'. コメント返しの確認 (004 / **未実施**)

**自分のコメントには反応しない**(`author-type="owner"` と「配信の持ち主の ID との一致」で弾く /
004 AC10)ので、**別アカウントからコメントできる環境が要る。**004 T12 はここが残っている。

手順:

1. 設定の **「コメントに反応して投稿する」を ON**(既定 OFF)
2. 辞書にそのアカウントのチャンネルを登録し、行を `▸` で開いて **「コメントに反応する」を ON**
   → **その場でチャンネルページを 1 回取得**し、`チャンネル ID: UC…` が出れば解決済み
   (出ない・⚠ が付く場合は理由が行に出る。**未解決の行はコメントに反応しない** / AC17)
3. テスト配信のチャットに、そのアカウントで書き込む

| 見るところ | 期待 |
|---|---|
| コンソール | `コメント返しの対象を検知した:` → `コメント返しを投稿する: …` |
| チャット | コメント用テンプレートの文面が投稿される (AC5) |
| チャット上部 | **固定されない**(`pinMode` に関わらず / AC6) |
| 2 回目のコメント | 投稿されない(`コメント返しをしない (この配信では投稿済み)` / AC7)。**`見送った` 側になるのは、1 通目の投稿が終わる前に 2 通目がキューへ積まれていた場合だけ**(投稿直前の再判断 / [comment-runner.ts](../src/comment-runner.ts)) |
| 自分の投稿 | それを引き金に再投稿しない(歯止め 3 枚 / AC10・plan.md R2) |
| ポップアウトの開き直し | 過去のコメントに一斉投稿しない(タイムスタンプ + 猶予 10 秒 / AC9・plan.md R3) |

### D. 失敗しても配信に影響しないことの確認 (AC6)

- 「リダイレクトを自動検知して投稿する」を OFF にする → 自動では投稿されない。手動トリガーからは投稿される (AC7)
- わざと壊す(例: オプションでテンプレートを空にする、DevTools で入力欄を消す)→
  コンソールに警告が出るだけで、チャットの操作・配信は続けられる

## 6. うまくいかないときの切り分け

すべて **DevTools コンソール(`live_chat` のフレーム)** で見る。

| 症状 | 見るログ | 原因と対処 |
|---|---|---|
| 何も起きない | `起動した {...}` が出ない | content script が注入されていない。URL が `studio.youtube.com/live_chat` か / 拡張が有効か / ⟳ を押したか |
| 「↩ 返礼」が出ない | `起動した {... showManualTrigger: false}` | 設定の「手動トリガーを出す」が OFF(既定) |
| リダイレクトを受けたのに反応しない | `[debug] 通知候補: {... matchedUnconfirmed: [...]}` | 通知の文言が**確認済みパターンに無い形**。`matchedUnconfirmed` に出た文言を `REDIRECT_TEXT_PATTERNS` へ昇格させる |
| `チャット入力欄が見つからない` | 同左 | `SELECTORS.chatInput` が外れている → 下の「セレクタの直し方」 |
| 投稿はされるが固定されない | `固定結果: unavailable` | `messageMenuButton` か `menuItems` / `PIN_MENU_LABELS` が外れている |
| 投稿はされるが `固定結果` が出ない | `投稿したメッセージ要素を特定できなかった` | `chatTextMessage` / `chatMessageText` が外れている(投稿自体は成立) |
| `ifEmpty` なのに既存の固定を消した | — | `pinnedBanner` が外れていて「固定なし」と誤判定した。当面 `off` にする |
| リダイレクトを受けたのに何も起きない | `投稿する (auto)` が出ない | 通知ノードを検出できていない。T1 の DOM 採取へ |
| チャットを開き直すたびに同じ相手へ投稿する | `起動した {...}` に `streamId` / `postLog` が**無い** | **古いビルドが動いている。**`npm run build` → `chrome://extensions` の ⟳ → チャットのリロード。読み込んでいるフォルダが目的の `dist/` かも確認する |
| 同上 | `起動した {... postLog: 0}` のまま増えない | 投稿履歴が保存できていない。`投稿履歴の保存 で例外:` が出ていないか見る |
| 同上 | `起動した {... streamId: '(不明)'}` | 配信 ID を取れていない(`v=` も親フレームの URL も読めない)。この場合は「同じ配信か」を判定できないので、履歴に対して 6 時間の下限をかけて抑止する。ポップアウト (`?is_popout=1&v=...`) を使えば確実に取れる |
| 投稿はされるが `固定結果: unavailable` | `メニューに「固定」項目が見つからない` | メニューは開けているが「固定」ラベルが無い。**対象が既に固定済みなら「固定を解除」しか出ない**(これは `pinned` として扱う)。それ以外は `PIN_MENU_LABELS` が外れている |
| 投稿されない・`この配信では投稿済みのためスキップ` | 同左(前回の文面と時刻が出る) | **抑止が効いている。**同じ配信で同じ相手には 1 回だけ。もう一度出すならオプションの投稿履歴を消す |
| コメントに反応しない | `起動した {... commentReplyEnabled: false}` | スイッチが OFF(既定)。**`enabled` とは別のスイッチ** |
| 同上 | `起動した {... replyToComment: 0}` | 辞書のフラグが 1 件も ON でない(設定画面が常時表示で同じことを言う / AC13) |
| 同上 | `起動した {... replyToComment: 3, commentReady: 0}` | フラグは ON だが **`channelId` が 1 件も解決できていない**。設定画面の「まとめて再試行」へ (AC17) |
| 同上 | `コメント返しをしない (辞書に該当が無い)` | **`channelId` が未解決の可能性が高い。**未解決の行は照合の対象外(AC17)。設定画面の ⚠ と「まとめて再試行」で直す。`UC…` が取れているのに当たらない場合は、**同じ `channelId` の行が 2 件以上ある**とやはり何もしない(常時表示の警告に出る) |
| 同上 | `コメント返しをしない (配信者自身のコメント)` | **自分のコメントには反応しない**(AC10)。別アカウントから試す |
| 同上(何も出ない) | 診断ログ ON で `[debug] コメントから投稿者を取れなかった:` / `[debug] 監視開始より前のコメントとして捨てた:` / `[debug] タイムスタンプを読めなかった。猶予だけで判定した` | 1 つ目は `whole-message-clickable` の中身が変わった可能性(plan.md R10)。**壊れ方は「何もしない」側**。2 つ目は AC9(監視開始より前のコメント)で正常。理由をそのまま記録する |
| 途中から出なくなった | `コメント返しを見送った (limit)` | **1 配信 20 件の上限**(AC11)。数えているのは投稿履歴の `kind='comment'` なので、リロードでは戻らない |

## 7. T1(実 DOM の採取)のやり方

自動検知を成立させるには、実際にリダイレクトを受けたときの DOM が要る。
ライブチャットのコンソールで以下を実行する。

**リダイレクト通知が出た直後に、チャット項目リストを丸ごと取る:**

```js
copy(document.querySelector('yt-live-chat-item-list-renderer')?.outerHTML)
```

**通知らしいカスタム要素を洗い出す(リダイレクト直後に実行):**

```js
[...new Set([...document.querySelectorAll('*')].map(e => e.tagName.toLowerCase()))]
  .filter(t => t.startsWith('yt-live-chat'))
```

**「固定中」のバナーを探す(何かを固定した状態で実行 / R4 の判定手段):**

```js
[...document.querySelectorAll('*')]
  .filter(e => /pinned|banner/i.test(e.tagName))
  .map(e => [e.tagName.toLowerCase(), e.id, e.textContent.trim().slice(0, 40)])
```

**メニュー項目のラベルを取る(自分のメッセージの ⋮ を手で開いた状態で実行):**

```js
[...document.querySelectorAll('[role="menuitem"], ytd-menu-service-item-renderer')]
  .map(e => [e.tagName.toLowerCase(), e.textContent.trim()])
```

> ⚠️ **採取した DOM には実在する第三者のチャンネル名・ハンドル・ID が入っている。**
> `tests/fixtures/` に入れる前に**必ず匿名化する**(`@example-channel` 等の架空値に置換)。
> ここは自動化せず目視で確認する(2026-08-02 に `obs-tachie-generator` で混入事故がある)。

採取できたら:

1. `src/selectors.ts` の該当セレクタを実 DOM の値に差し替える(`TODO(T1)` を消す)
2. `tests/fixtures/live-chat.ts` の合成 DOM を、匿名化した実 DOM に差し替える
3. `npm run typecheck && npx vitest run`
4. **落ちたテストは実装側を直す。**fixture を実装に合わせて歪めない

### ストア提出用の ZIP を作る

```bash
npm run package:store
```

`release/shoutlink-<version>-store.zip` ができる(ビルドも一緒に走る)。
**`npm run package`(Releases 用)とは別物。**取り違えるとどちらも通らない。

```
shoutlink-0.3.0-store.zip
  manifest.json    ← **ルート直下**。ストアはここに manifest が無いと弾く
  content.js / options.html / options.js / icons/
```

| | Releases 用 (`package`) | ストア用 (`package:store`) |
|---|---|---|
| 包み | `shoutlink-<version>/` で 1 枚包む | **包まない**(ルートに `manifest.json`) |
| `INSTALL.txt` | **入れる**(デベロッパーモード読み込みの手順) | **入れない**(手順が食い違う) |
| `key` | 入れる | **落とす**(→ 上の「ストアへ移すと拡張 ID が変わる」) |

**`public/manifest.json` と `dist/` の `key` はそのまま。**書き換えるのは ZIP へ入れる分だけなので、
`npm run package:store` を流しても手元の拡張 ID は動かない。

`package-store.mjs` は作る前に落ちる検査を持っている。**黙って壊れた ZIP を吐かない:**

- `package.json` と `manifest.json` の版が食い違っていたら止まる
- 必須ファイル(`manifest.json` / `content.js` / `options.html` / `options.js` / アイコン)が
  欠けていたら止まる
- **リモートコードらしきものがあったら止まる** — `eval()` / `new Function()` /
  `importScripts()` / 動的 `import()` / HTML の外部 `src`・`href`。
  ストアの申告(リモートコードなし)と提出物が食い違わないようにするため。
  ⚠️ **「ネットワークに一切触らない」ことの確認ではない。** 設定ページは
  `www.youtube.com` のチャンネルページを 1 回 GET する(AC17)。
  **取得した HTML を読むだけでコードとして実行しない**ので、この検査では落とさない

### ストアへ移すと拡張 ID が変わる (2026-08-23 決定)

**結論: 設定・辞書・投稿履歴は引き継がれない。ストア版は別の拡張として扱われる。**

**一次情報:** [Keep a consistent extension ID](https://developer.chrome.com/docs/extensions/reference/manifest/key)
が示す手順は **「まずダッシュボードへ ZIP を上げる → Package タブの View public key で公開鍵を取る →
それを `manifest.json` の `key` に入れる」**。つまり**鍵と ID を作るのはストア側**で、
こちらの `key` を持ち込む手順ではない。
`public/manifest.json` にいま入っている自前の `key`(0.3.0 で追加)から決まるローカル ID と、
**ストアが割り当てる ID は一致しない。**

**決めたこと:**

1. **`key` はストア提出用 ZIP から外す**(→ `npm run package:store`)。
   - `public/manifest.json`(開発用)からは**外さない。**ローカルの ID が動くと開発中に困る。
   - ~~初回アップロードの後、Package タブの公開鍵を `public/manifest.json` の `key` へ入れ替える。~~
     → **2026-08-23 に実施済み。** ローカルビルドの ID は
     **`kpjfmcppkncdmehdpgcochaanbmodaim`**(ストアのアイテム ID と同じ)になった。
     旧 ID は `bfmfamnekclamfdjbfndmomljgneejgo`。
     **これは既存利用者の移行にはならない** — 既に入っている版は旧 ID のまま。
   - 補足: 新規アイテムの初回アップロードで `key field is not allowed in manifest` が出るという報告が
     [chromium-extensions (2021)](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/x_NBS6_-NKs)
     にある。**コミュニティの報告で公式の記述ではなく、常に出るとは限らない。**
     外しておけばどちらでも通るので、外す。
2. **移行は手作業で行う。エクスポート / インポート機能は作らない**(2026-08-23 / 人間)。
   - **いま辞書を育てて使っているのは自分だけ**なので、他人に配れる移行機能は要らない。
     設定・辞書の JSON エクスポート / インポートは**あると便利だが、掲載の前提ではない**
     (作るとしても後回しの単独 feature。ストア版になれば自動更新が効くので、後から足すほうが楽)。
   - **順番は「先に控える → 旧版を削除 → ストア版を入れる → 書き戻す」。**
     **削除がストア版より先。** 並存させると **ID が違うので Chrome の重複防止
     (「同じ ID の拡張機能が既にあります」) が効かず、両方が動いて同じ相手へ 2 回投稿する。**

   **控えかた / 書き戻しかた。** 設定ページは拡張オリジンで動くので、その DevTools から
   ストレージを丸ごと出し入れできる(`storage` 権限は既にある)。保存先は
   `ytRedirectPin.config` が `sync`、`ytRedirectPin.directory` と `ytRedirectPin.postLog` が
   `local` だが、**`get(null)` で全部取れるのでキーを覚える必要はない。**

   ```js
   // ① 旧版の設定ページ (chrome-extension://<旧 ID>/options.html) の DevTools コンソール
   Promise.all([chrome.storage.local.get(null), chrome.storage.sync.get(null)])
     .then(([local, sync]) => copy(JSON.stringify({ local, sync })))
   // → クリップボードに入った JSON をファイルへ保存しておく

   // ② 旧版を削除 → ストア版を入れる → ストア版の設定ページの DevTools コンソール
   const saved = /* ① の JSON を貼る */
   Promise.all([chrome.storage.local.set(saved.local), chrome.storage.sync.set(saved.sync)])
     .then(() => location.reload())
   ```

   ⚠️ **投稿履歴 (`ytRedirectPin.postLog`) も一緒に書き戻す。** 捨てると再投稿の抑止が白紙になり、
   同じ配信で既に返礼した相手へもう一度投稿しうる。
3. **移行手順の文言の置き場** — **自分用の手順なので掲載文には書かない。**
   要るのは、**デベロッパーモード版を入れている人に「先に旧版を削除する」「設定は引き継がれない」を
   伝えること**だけ。置き場は `README.md` の入れかた / [install.md](install.md) の
   「新しい版に入れ替える」 / [for-testers.md](for-testers.md)。
   - **「設定は引き継がれます」と書いてある現在の記述**(install.md L52・L68 / `INSTALL.txt` /
     `README.md` L85)は、**いまは正しいがストア版には当てはまらない。**そのまま残すと嘘になる。

どのファイルが何を持つか。**DOM に触る箇所と、純関数として切り出した箇所**の
区別がテストの書きやすさを決めるので、そこを軸に並べる。

| ファイル | 役割 |
|---|---|
| `src/selectors.ts` | **主要な DOM セレクタの集約点。** 候補の配列を先頭から試す。原則ここに置き、他モジュールで `document.querySelector` を直接呼ばない (`detector.ts` `pinner.ts` には局所的な例外が残っている) |
| `src/detector.ts` | MutationObserver → `RedirectEvent`。抽出部は純関数 (`extractRedirectEvent`) として分離 |
| `src/comment-detector.ts` | コメント返しの検知。**追加されたコメントだけ**を見る (既存のコメントは拾わない)。抽出部は純関数 (`extractCommentAuthor`) |
| `src/comment-reply.ts` | コメント 1 件に返すかどうかの判断(純関数)。**自己ループの遮断を辞書の照合より先に置く。**照合は `channelId` のみで、抑止は種別を問わない (AC7 / AC8 / AC10) |
| `src/comment-runner.ts` | コメント経路の配線。検知 → 判断 → キュー → 投稿。**キューに積んだ後、投稿の直前にもう一度判断する**(順番待ちの間に状況が変わるため) |
| `src/post-queue.ts` | コメント返しの逐次処理。最低 5 秒間隔 / 1 配信 20 件の上限 / 無効化時に未処理を捨てる。**間隔の起点はメモリのみ**(リロードで戻る) |
| `src/channel-id.ts` | チャンネルページから照合用の `UC…` を取り出す。**設定画面からしか呼ばない** (チャット画面では通信しない) |
| `src/composer.ts` | テンプレート差し込み (`{name}` `{url}` `{msg}`) |
| `src/directory.ts` | 相手ごとの辞書 (`chrome.storage.local`)。呼び名 / リダイレクト返礼用の自由文 (`message`) / **コメントに反応するか (`replyToComment`)** / **コメント返し用の自由文 (`commentMessage`)** / **照合用のチャンネル ID (`channelId`)**。**端末間で同期しない。**`sync` からは 1 度だけ引き継ぐ(`sync` 側は消さない) |
| `src/dedupe.ts` | 同一送信元・クールダウンの多重発火抑止。**クールダウンは同一配信内でのみ適用**(配信が違えば通す)。**配信 ID が無く、かつ前の起動から読み戻した記録**にだけ 6 時間の下限を当てる (`cooldownSec = 0` は下限ごと外す逃げ道) |
| `src/post-log.ts` | 投稿履歴 (`chrome.storage.local`)。**リロードをまたいで再投稿を止める土台。**誰に・何を・いつ・どの配信で・**どちらの種別で** (リダイレクト返礼 / コメント返し) |
| `src/poster.ts` | チャット入力欄への投稿と、投稿した自分のメッセージ要素の特定 |
| `src/pinner.ts` | `PinMode` の解釈と「固定」の実行 |
| `src/manual-trigger.ts` | 手動トリガー UI(設定 `showManualTrigger` / **既定 OFF**)。自動検知と同じ `RedirectEvent` を同じパイプラインに流す |
| `src/self-echo.ts` | 自分の投稿(とその固定バナー)を通知として拾い直す自己ループの抑止。**設定と独立** |
| `src/config.ts` | `chrome.storage.sync` への設定の永続化と、`local` を使う側の入口 |
| `src/main.ts` | 配線。全体を try/catch (AC6) |

## 9. 既知の制約

- **ブラウザを開きっぱなしにする必要がある。**ライブチャットのページが閉じていれば何も動かない。
- 投稿にはログイン済みのブラウザセッションを使う。名義はそのブラウザでログインしているアカウント。
- チャットへの URL 投稿が**スパムフィルタで弾かれる可能性**がある(plan.md R2)。
  弾かれるなら、テンプレートから `{url}` を外して `{name}` と `@ハンドル` だけの文面にする。
- ライブチャットの 1 メッセージの文字数上限は 200 と仮定している(未検証)。
  超える場合は表示名を削り、URL は壊さない。
- 「固定」に確認ダイアログが挟まるかは未確認。挟まる場合、現状の実装では固定が完了しない。
