# 004 T1 — コメントの投稿者を特定できるか実 DOM で採取する

対応: [specs/004-comment-link/tasks.md](../specs/004-comment-link/tasks.md) T1 / issue #25 /
[spec.md](../specs/004-comment-link/spec.md) の「この feature の成立条件」

**この文書は手順書であり、採取結果の置き場でもある。**実施したら末尾の「採取結果」に追記する。

---

## 何を採るか

004 は「辞書に載っている人がコメントしたら、その人のチャンネル URL を投稿する」機能で、
**照合の鍵は正規化済みチャンネル URL**(`normalizeChannelUrl` の出力)。
その鍵がコメント側から取れなければ feature が成立しない。採るのは 3 点。

| # | 採るもの | 効く受け入れ条件 |
|---|---|---|
| ① | コメント要素から**投稿者のチャンネル**が取れるか(属性・リンク) | AC4 |
| ② | 取れる形が `@handle` / `UC…` のどちらで、**辞書の鍵と同じ正規形**になるか | AC4 / spec.md D1 |
| ③ | **配信者自身の投稿**を見分ける手掛かりと、**メッセージのタイムスタンプ** | AC10 / AC9 / spec.md D2 |

あわせて、項目リストに実際に出ている**要素の内訳**も採る(AC3 の「通常のテキストコメントだけ」を
どの要素で切るかは、`SELECTORS.chatTextMessage` の流用が禁じられているため自前で決める必要がある)。

> **採れなかった場合に何を採るかは人間が決める**(spec.md D1 / D2)。
> 「表示名で照合すればとりあえず動く」は**この文書の範囲外**であり、
> エージェントがその判断へ降りてはいけない(plan.md R1 / R2)。

## 安全性

- **スクリプトは読み取りしかしない。**投稿もクリックもメニュー操作もしない。
- **出力は既定で匿名化される。**ハンドル・表示名・チャンネル ID・本文は「形と文字数」に置き換わる。
  この repo は public で、[docs/t1-findings.md](t1-findings.md) も
  「構造(タグ名・id・属性名・要素数)だけを記録する」方針で書かれている。
- `YTRP.raw(i)` だけは**生の値**を出す。形を自分の目で確かめるためのもので、
  **その出力は docs / issue / PR へ貼らない。**
- 拡張は動いたままでよい(004 の機能はまだ無いので、コメントで何かが起きることはない)。

## 準備

1. **自分のテスト配信を 1 本立てる**(限定公開でよい)。
2. チャットに**何種類かのコメントを出しておく**。多いほど採取が確実になる。
   - **自分(配信者)から** — ③の「自分の判別」に必須
   - **別のアカウントから** — 別ブランドアカウント / 別端末 / 協力者のいずれか。
     **これが無いと「他人のコメントから取れるか」が確かめられない**(自分のコメントだけだと、
     配信者だから取れているのか誰でも取れるのか区別がつかない)
   - あれば**スパチャ・メンバー加入・削除済みのメッセージ**も(AC3 の除外対象の要素名を採るため)

## 実行場所

**動かすのは `studio.youtube.com/live_chat*` だけ。**`www.youtube.com` 側は拡張が意図的に
動かない画面なので、そこで採った DOM を根拠にしない。

| 開き方 | DevTools の操作 |
|---|---|
| **ポップアウト**(推奨)<br>`https://studio.youtube.com/live_chat?is_popout=1&v=<動画ID>` | **フレームの切り替えは不要**(トップレベル文書) |
| **管制室に埋め込まれたチャット**<br>`https://studio.youtube.com/video/<動画ID>/livestreaming` | チャットは **iframe**。コンソール左上のフレーム選択(既定 `top`)を **`live_chat`** に切り替える。切り替えないとチャットの DOM が一切見えない |

> ポップアウトで別のログインアカウントに切り替わってしまう場合は `&authuser=N`(0,1,2…)、
> ブランドアカウントなら `&pageId=UC...` を付ける([docs/t1-findings.md](t1-findings.md) の詰まり所)。

## 手順

### 1. スクリプトを貼る

[scripts/t1-comment-probe.js](../scripts/t1-comment-probe.js) を**丸ごとコピー**して、
上の画面の DevTools コンソールに貼って実行する。次のように出れば準備完了。

```
[YTRP] 用意できた。順に実行する:
  1) YTRP.probe()      … いま出ているコメントを調べる
  ...
```

`チャット項目リストが見つからない` と出たら、**フレームの切り替えを忘れている**(上の表)。

### 2. いま出ているコメントを調べる

```js
YTRP.probe()
```

表が 2 つ出る。

- **項目リストに出ている要素の内訳** — `yt-live-chat-text-message-renderer` が何件、
  スパチャ・メンバー加入・その他が何件。**AC3 でどの要素を対象にするか**の材料
- **直近のメッセージ** — 1 行 1 件で、次の列を見る

| 列 | 読み方 |
|---|---|
| **`DOM属性から投稿者`** | **ここが本命。**`whole-message-clickable` 属性から取り出した投稿者の ID を、ページ内部の正解と突き合わせた結果。**`一致` なら拡張(content script)から投稿者を特定できる**。`不一致` なら切り分けが間違っている。`取れない(…)` は理由つき |
| `UC の個数` | 上の属性の中に `UC…` が何個あったか。**持ち主 + 投稿者で 2 個**が想定 |
| **`属性内のハンドル`** | 同じ属性の中に `@ハンドル` らしい値があるか。**あれば辞書の鍵とそのまま一致する**ので、対応付けが要らなくなる |
| `DOMで取れる` | 属性値やリンクに**生の文字列として**現れる ID。base64 に埋もれているものはここに出ない(`—` でも `DOM属性から投稿者` が `一致` なら取れている) |
| `DOMの出所` | 上がどの要素・どの属性から取れたか |
| `Polymerで取れる` | **参考にしかならない**(下の「ワールドの区別」)。**正解の照合用** |
| **`Polymerのハンドル(URL系)`** | ページ内部に `@ハンドル` らしい値があるか。**表示名(`author*`)は除いてある** |
| `表示名が@形式` | 参考。**表示名は鍵にしない**(チャンネル名は誰でも自由に決められる) |
| `author-type` | ③の材料。配信者のコメントで `owner` が入るか |
| `バッジ` | ③の材料。`author-type` が無い場合の代わり |
| `timestamp(DOM)` | ③の材料。`5:17 PM` のような**時計表記**なら AC9 に使える。`0:12` のような**配信開始からの相対時刻**なら使えない |
| `timestamp(Polymer)` | 絶対時刻(µs)が入りうる。ただし下記のとおり拡張からは見えない |

### 3. 新しく現れるコメントを拾う

```js
YTRP.watch(60)
```

60 秒間、**新しく追加されたコメント**だけを拾う。**この間に自分でも 1 回コメントする。**
終わると表が出る。見るのは 2 点。

- 自分のコメントの行で `author-type` に何が入るか(**③ = AC10 の 3 枚目**)
- `Polymer時刻と現在の差(秒)` が 0 前後か(タイムスタンプが**絶対時刻**として使えるか / AC9)

### 4. 結果を出す

```js
YTRP.show()
```

匿名化済みの Markdown が `console.log` で出るので、**選択してコピー**し、
この文書の末尾「採取結果」へ貼る。貼る前に、ハンドル・表示名・チャンネル ID が
**残っていないことを目で確かめる**。

> **`copy(YTRP.md())` は使えないことがある。** studio.youtube.com では
> `copy is not a function` になった(2026-08-15)。`YTRP.show()` はただの `console.log` なので必ず出る。

必要なら個別に詳しく見る。**コンソールに出る内容は匿名化済み**(戻り値は返さない)。

```js
YTRP.detail(0)   // 0 は表の「#」列の番号
```

> ⚠️ **`YTRP.raw(i)` と `YTRP.state` は生の値を出す。**形を自分の目で確かめるためのもので、
> **その出力は docs / issue / PR へ貼らない。**

## ⚠️ ワールドの区別 — 「コンソールで取れた」は「拡張から取れる」ではない

DevTools のコンソールは**ページと同じメインワールド**で動く。一方、拡張の content script は
**隔離ワールド**で動く。両者は同じ DOM を見るが、**ページの JS が要素に付けたプロパティは
隔離ワールドからは見えない。**

| 出所 | コンソール | content script |
|---|---|---|
| 属性・`href`・テキスト(`DOM属性から投稿者` / `DOMで取れる` 列) | 見える | **見える** |
| Polymer のプロパティ `__data` 等(`Polymerで取れる` 列) | 見える | **見えない** |

したがって、**`Polymerで取れる` にだけ値が出て DOM 側が全部 `—` の場合、
今の構成のままでは投稿者を特定できない。**そのときはメインワールドへの注入を許すかどうかの
判断になる(**注入範囲を広げる設計変更**なので spec.md D1 に含めて人間が決める)。

> **今回はその判断に至らなかった。**DOM 属性(`whole-message-clickable`)から取れたため
> **注入は不要**と確定している(下の「採取結果」)。**この節は、次に採り直すときのための説明として残す。**

## 結果の読み方 — どの分岐に落ちるか

**判断そのものは人間が行う**(spec.md D1 / D2)。この表は材料の整理でしかない。

| `DOM属性から投稿者` / `属性内のハンドル` の結果 | 意味 | 次 |
|---|---|---|
| `一致` かつ `属性内のハンドル` あり | 辞書の鍵と**同じ正規形**で取れる。AC4 がそのまま成立 | T7 へ進める。対応付けは要らない |
| `一致` だが ID は `UC…` だけ | 取れるが**鍵の形が違う**。`findEntry` は文字列比較なので**永久に空振り**する | spec.md **D1 (c)**(対応付けを作る)を人間が判断 ← **今回はここ** |
| `不一致` がある | 切り分けが間違っている | この経路は使えない。採り直す |
| DOM 側が全部 `—`(Polymer にはある) | content script からは取れない | spec.md **D1**。注入範囲を広げるかを含めて人間が判断 |
| どこにも無い | 投稿者を特定できない | spec.md **D1 (a) / (b) / (d)** を人間が判断 |

| ③ の結果 | 意味 | 次 |
|---|---|---|
| `author-type` かバッジで配信者を判別できる | AC10 の歯止め 3 枚目が成立 | そのまま実装できる ← **今回はここ** |
| 判別できない | 歯止めが実質「本文一致」1 枚になる | spec.md **D2**(1 枚欠けた状態で出すか)を人間が判断 |
| タイムスタンプが**時計表記**で取れる | AC9 を時刻で切れる(**分単位**なら同じ分は猶予頼み) | そのまま実装できる ← **今回はここ** |
| 相対時刻しか無い / 取れない | AC9 は「監視開始から 10 秒の猶予」に落ちる。猶予は起動直後しか塞げない | spec.md **D2** に含めて人間が判断 |

## 採取結果

**採取日: 2026-08-14 〜 15** / 対象: `studio.youtube.com/live_chat*` の実配信(ポップアウト)/
チャット項目 12〜19 件(`yt-live-chat-text-message-renderer` と
`yt-live-chat-viewer-engagement-message-renderer` 1 件)。
**配信者自身の投稿と、別の視聴者の投稿の両方**を含む。`YTRP.probe()` と `YTRP.watch(60)` を実施。

### 確定した内容

| 採取項目 | 結果 |
|---|---|
| ① 投稿者のチャンネル | **取れる。**ただし**リンクやテキストとしてではなく**、**DOM 属性 `whole-message-clickable` の中**(base64 を 2 回解いた先)。→ 下の「どう取れるか」 |
| ② 形 | **`UC…`(24 字)。** 辞書の鍵は `@handle` 側なので**正規形が一致しない** → **対応付けが要る**(spec.md D1 (c)) |
| ② ハンドル | **見つからなかった** → 下の「探した範囲」 |
| ③ 配信者自身の判別 | **`author-type` 属性が DOM で取れる。**配信者の投稿は `owner`、他の視聴者は空文字。**追加ノードにも付く**(`YTRP.watch` で確認) |
| ③ タイムスタンプ(DOM) | `#timestamp` のテキストが **`5:17 PM` 形式**(時計の絶対時刻だが**分単位・日付なし**) |
| ③ タイムスタンプ(Polymer) | µs の絶対 epoch。**追加された瞬間との差が 0 秒**だったので本物の絶対時刻。ただし**隔離ワールドからは見えない** |
| AC3 の対象 | 通常のコメントは `yt-live-chat-text-message-renderer`。システムメッセージ(`viewer-engagement-message-renderer`)は投稿者が存在しないので自然に外れる |
| バッジ | `type` / `aria-label` を持つバッジは**採れていない**(初回は中身の `span` を拾っていた。プローブ側を修正済み)。**③ は `author-type` で足りる** |

### ① どう取れるか — `whole-message-clickable`(DOM 属性)

メッセージ要素の DOM 属性に `liveChatItemContextMenuEndpoint.params` が入っており、
**base64 を 2 回**解くと protobuf が出る。

```
params → base64 → base64 → protobuf
  ├ メッセージ ID
  ├ { チャンネルID, 動画ID }   ← 動画とセット = 配信の持ち主
  └ { チャンネルID }           ← 投稿者
```

初回の探索が当たらなかったのは、**属性値の中で `UC…` が base64 に埋もれていて
そのままの文字列としては現れない**ため(生の `UC` / `@` を探していた)。

**検証**: 取り出した ID を、ページ内部の `authorExternalChannelId`(正解)と 1 件ずつ突き合わせた。
**通常のテキストメッセージは全件「一致」。**取れなかったのはシステムメッセージだけで、
投稿者が存在しないので正常。**`UC…` は毎回ちょうど 2 個**(持ち主 + 投稿者)だった。

- **DOM 属性なので content script(隔離ワールド)から読める** → **メインワールドへの注入は要らない**
- ⚠️ **これは公開された仕様ではない。**フィールド番号・順序が変われば壊れる。
  そのため**「2 つ目を採る」のような位置頼みにしない** — **動画 ID とペアになっているほうを
  配信の持ち主として除外**する。**持ち主を特定できない / 候補が 2 つ以上ある /
  残りが 1 つに絞れない場合は「取れなかった」として扱う**(推測しない)
- ⚠️ **「ペアになっている」の測り方は 2 段階あり、確からしさが違う**
  (2026-08-15 のレビューで区別した):
  - **実測したのは「`UC…` の直後 20 バイトの窓に、今見ている配信の動画 ID がそのまま入っているか」**。
    プローブが使ったのはこの形で、全メッセージで正解と一致した
  - **protobuf の `12 <長さ> <文字列>` という並びまでは測っていない。**
    実装はこれも見るが、**それは推論**で、**配信 ID が取れない画面
    (管制室の埋め込みチャット)での唯一の手段**として置いてある。
    外れれば全件が「切り分けられない」に落ちて**機能が無言で止まる**ので、
    どちらで当たったかを診断ログに出す

### ② ハンドルを探した範囲 — **見つからなかった**

**「どこにも無い」と断定はできない。**探したのは次の範囲で、そこには無かった。

| 探した場所 | 方法 | 結果 |
|---|---|---|
| DOM の属性値・リンク・テキスト | 生の `UC` / `/@` / `@…` の文字列 | 無し(唯一の `<a>` は翻訳の「原文を表示」) |
| `whole-message-clickable` の**復号後** | `@…` の形の値を全部拾う | 無し(**`UC…` は 2 個ある**) |
| ページ内部のデータ | キー名に頼らず `@…` の形の値を拾う(深さ 5、最初に当たったコンテナ 1 つ) | **`authorName.simpleText` の 1 件だけ** |

⚠️ **`authorName.simpleText` は表示名であってハンドルではない。**
チャンネル名は誰でも自由に決められるので、形が `@…` でも「その人のハンドル」である保証がない。
**これを鍵にするのは spec.md D1 (a)(表示名照合)そのもの**で、同名の別人・改名・なりすましで
**別人のリンクを貼る。**

→ したがって **`UC…` と辞書の鍵(`@handle`)をつなぐ対応付け(D1 (c))が要る。**

### 決定(spec.md D1 / D2 — 正本は [spec.md](../specs/004-comment-link/spec.md))

- **投稿者は DOM 属性から取る。メインワールドへの注入はしない。**
  2026-08-14 に一度「注入を許す」と決めたが、**DOM 属性から取れると分かって前提が消えた**
- **表示名照合には降りない**
- **`channelId` を辞書に足し、チャンネルページから解決する**(AC17)。
  これに伴い `host_permissions` に `https://www.youtube.com/*` が増える
- **D2(歯止めが 1 枚欠けた状態で出すか)は解消。**`author-type` もタイムスタンプも取れるので
  **歯止めは 3 枚とも揃う**

### 採取そのものについて分かったこと(プローブの修正点)

- **戻り値をコンソールが展開すると、匿名化を素通りして生のチャンネル ID が出る。**
  `probe()` は匿名化済みの表を返す形に、`detail()` は**何も返さない**形にした
- **`copy()`(DevTools のコマンドラインAPI)は studio.youtube.com で使えなかった。**
  `YTRP.show()` を足して `console.log` で出す形にした
- **キー名で絞ると探し漏れる。**初回は `channel` / `author.*id` / `externalId` で絞っていて、
  ハンドルが入りうるキーを最初から見ていなかった。**値の形で探す**経路を足した
- **`aria-label` は自由文なので伏せる**(列挙値・真偽値だけを生のまま出す)
