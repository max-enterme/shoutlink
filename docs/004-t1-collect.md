# 004 T1 — コメントの投稿者を特定できるか実 DOM で採取する

対応: [specs/004-comment-link/tasks.md](../specs/004-comment-link/tasks.md) T1 / issue #25 /
[spec.md](../specs/004-comment-link/spec.md) の「この feature の成立条件」

**この文書は手順書であり、採取結果の置き場でもある。**実施したら末尾の「採取結果」に追記する。

---

## 何を採るか

004 は「辞書に載っている人がコメントしたら、その人のチャンネル URL を投稿する」機能で、
**照合の鍵は正規化済みチャンネル URL**(`normalizeChannelUrl` の出力)。
その鍵がコメント側から取れなければ feature が成立しない。採るのは 3 点。

| # | 採るもの | 効く受け入れ条件 |
|---|---|---|
| ① | コメント要素から**投稿者のチャンネル**が取れるか(属性・リンク) | AC4 |
| ② | 取れる形が `@handle` / `UC…` のどちらで、**辞書の鍵と同じ正規形**になるか | AC4 / spec.md D1 |
| ③ | **配信者自身の投稿**を見分ける手掛かりと、**メッセージのタイムスタンプ** | AC10 / AC9 / spec.md D2 |

あわせて、項目リストに実際に出ている**要素の内訳**も採る(AC3 の「通常のテキストコメントだけ」を
どの要素で切るかは、`SELECTORS.chatTextMessage` の流用が禁じられているため自前で決める必要がある)。

> **採れなかった場合に何を採るかは人間が決める**(spec.md D1 / D2)。
> 「表示名で照合すればとりあえず動く」は**この文書の範囲外**であり、
> エージェントがその判断へ降りてはいけない(plan.md R1 / R2)。

## 安全性

- **スクリプトは読み取りしかしない。**投稿もクリックもメニュー操作もしない。
- **出力は既定で匿名化される。**ハンドル・表示名・チャンネル ID・本文は「形と文字数」に置き換わる。
  この repo は public で、[docs/t1-findings.md](t1-findings.md) も
  「構造(タグ名・id・属性名・要素数)だけを記録する」方針で書かれている。
- `YTRP.raw(i)` だけは**生の値**を出す。形を自分の目で確かめるためのもので、
  **その出力は docs / issue / PR へ貼らない。**
- 拡張は動いたままでよい(004 の機能はまだ無いので、コメントで何かが起きることはない)。

## 準備

1. **自分のテスト配信を 1 本立てる**(限定公開でよい)。
2. チャットに**何種類かのコメントを出しておく**。多いほど採取が確実になる。
   - **自分(配信者)から** — ③の「自分の判別」に必須
   - **別のアカウントから** — 別ブランドアカウント / 別端末 / 協力者のいずれか。
     **これが無いと「他人のコメントから取れるか」が確かめられない**(自分のコメントだけだと、
     配信者だから取れているのか誰でも取れるのか区別がつかない)
   - あれば**スパチャ・メンバー加入・削除済みのメッセージ**も(AC3 の除外対象の要素名を採るため)

## 実行場所

**動かすのは `studio.youtube.com/live_chat*` だけ。**`www.youtube.com` 側は拡張が意図的に
動かない画面なので、そこで採った DOM を根拠にしない。

| 開き方 | DevTools の操作 |
|---|---|
| **ポップアウト**(推奨)<br>`https://studio.youtube.com/live_chat?is_popout=1&v=<動画ID>` | **フレームの切り替えは不要**(トップレベル文書) |
| **管制室に埋め込まれたチャット**<br>`https://studio.youtube.com/video/<動画ID>/livestreaming` | チャットは **iframe**。コンソール左上のフレーム選択(既定 `top`)を **`live_chat`** に切り替える。切り替えないとチャットの DOM が一切見えない |

> ポップアウトで別のログインアカウントに切り替わってしまう場合は `&authuser=N`(0,1,2…)、
> ブランドアカウントなら `&pageId=UC...` を付ける([docs/t1-findings.md](t1-findings.md) の詰まり所)。

## 手順

### 1. スクリプトを貼る

[scripts/t1-comment-probe.js](../scripts/t1-comment-probe.js) を**丸ごとコピー**して、
上の画面の DevTools コンソールに貼って実行する。次のように出れば準備完了。

```
[YTRP] 用意できた。順に実行する:
  1) YTRP.probe()      … いま出ているコメントを調べる
  ...
```

`チャット項目リストが見つからない` と出たら、**フレームの切り替えを忘れている**(上の表)。

### 2. いま出ているコメントを調べる

```js
YTRP.probe()
```

表が 2 つ出る。

- **項目リストに出ている要素の内訳** — `yt-live-chat-text-message-renderer` が何件、
  スパチャ・メンバー加入・その他が何件。**AC3 でどの要素を対象にするか**の材料
- **直近のメッセージ** — 1 行 1 件で、次の列を見る

| 列 | 読み方 |
|---|---|
| `DOMで取れる` | **ここが本命。**`@handle` / `UC…` なら、**拡張(content script)から取れる**。`—` なら取れない |
| `DOMの出所` | どの要素・どの属性から取れたか。`selectors.ts` に入れる形はここから決める |
| `Polymerで取れる` | **参考にしかならない**(下の「ワールドの区別」) |
| `author-type` | ③の材料。配信者のコメントで `owner` 等が入るか |
| `バッジ` | ③の材料。`author-type` が無い場合の代わり |
| `timestamp(DOM)` | ③の材料。`0:12` のような**配信開始からの相対時刻**なら、AC9 の「監視開始より前か」の判定には使えない |
| `timestamp(Polymer)` | 絶対時刻(µs)が入りうる。ただし下記のとおり拡張からは見えない |

### 3. 新しく現れるコメントを拾う

```js
YTRP.watch(60)
```

60 秒間、**新しく追加されたコメント**だけを拾う。**この間に自分でも 1 回コメントする。**
終わると表が出る。見るのは 2 点。

- 自分のコメントの行で `author-type` に何が入るか(**③ = AC10 の 3 枚目**)
- `Polymer時刻と現在の差(秒)` が 0 前後か(タイムスタンプが**絶対時刻**として使えるか / AC9)

### 4. 結果を貼り戻す

```js
copy(YTRP.md())
```

クリップボードに匿名化済みの Markdown が入る。**この文書の末尾「採取結果」へ貼る。**
貼る前に、ハンドル・表示名・チャンネル ID が**残っていないことを目で確かめる**。

必要なら個別に詳しく見る(こちらも匿名化済み)。

```js
YTRP.detail(0)   // 0 は表の「#」列の番号
```

## ⚠️ ワールドの区別 — 「コンソールで取れた」は「拡張から取れる」ではない

DevTools のコンソールは**ページと同じメインワールド**で動く。一方、拡張の content script は
**隔離ワールド**で動く。両者は同じ DOM を見るが、**ページの JS が要素に付けたプロパティは
隔離ワールドからは見えない。**

| 出所 | コンソール | content script |
|---|---|---|
| 属性・`href`・テキスト(`DOMで取れる` 列) | 見える | **見える** |
| Polymer のプロパティ `__data` 等(`Polymerで取れる` 列) | 見える | **見えない** |

したがって、**`Polymerで取れる` にだけ値が出て `DOMで取れる` が `—` の場合、
今の構成のままでは投稿者を特定できない。**(メインワールドへスクリプトを注入すれば読めるが、
それは注入範囲を広げる設計変更で、**この feature の前提が変わる。**
その判断は spec.md D1 に含めて人間が行う。)

## 結果の読み方 — どの分岐に落ちるか

**判断そのものは人間が行う**(spec.md D1 / D2)。この表は材料の整理でしかない。

| `DOMで取れる` の結果 | 意味 | 次 |
|---|---|---|
| `@handle` | 辞書の鍵と**同じ正規形**。AC4 がそのまま成立 | T7 へ進める。`DOMの出所` を `selectors.ts` に入れる |
| `UC…` | 取れるが**鍵の形が違う**。`findEntry` は文字列比較なので**永久に空振り**する | spec.md **D1 (c)**(対応付けを作る)を人間が判断 |
| `—`(Polymer にはある) | content script からは取れない | spec.md **D1**。注入範囲を広げるかを含めて人間が判断 |
| `—`(どこにも無い) | 投稿者を特定できない | spec.md **D1 (a) / (b) / (d)** を人間が判断 |

| ③ の結果 | 意味 | 次 |
|---|---|---|
| `author-type` かバッジで配信者を判別できる | AC10 の歯止め 3 枚目が成立 | そのまま実装できる |
| 判別できない | 歯止めが実質「本文一致」1 枚になる | spec.md **D2**(1 枚欠けた状態で出すか)を人間が判断 |
| タイムスタンプが**絶対時刻**で取れる | AC9 を時刻で切れる | そのまま実装できる |
| 相対時刻しか無い / 取れない | AC9 は「監視開始から 10 秒の猶予」に落ちる。猶予は起動直後しか塞げない | spec.md **D2** に含めて人間が判断 |

## 採取結果

**採取日: 2026-08-14** / 対象: `studio.youtube.com/live_chat*` の実配信 / チャット項目 12 件
(`yt-live-chat-text-message-renderer` 11 + `yt-live-chat-viewer-engagement-message-renderer` 1)。
配信者自身の投稿と、別の視聴者の投稿の両方を含む。

> **監視(`YTRP.watch`)の結果は未取得。**追加ノードが同じ属性を持つか(AC9 / AC10)はまだ見ていない。

| 採取項目 | 結果 |
|---|---|
| ① 投稿者のチャンネル(**DOM**) | **取れる**(下の 4. / 2026-08-15 に確定)。ただし**リンクやテキストとしてではなく**、`whole-message-clickable` 属性の中の base64 の中。~~取れない~~ |
| ① 投稿者のチャンネル(**Polymer**) | 取れる。`data.authorExternalChannelId`(**正解の照合用に使った**。実装では使わない) |
| ② 形 | **取れたのは `UC…`(24 字)。** 辞書の鍵は `@handle` 側なので、これだけだと正規形が一致しない。**ただし「ハンドルがどこにも無い」ことは確かめていない**(下記) |
| ③ 配信者自身の判別 | **`author-type` 属性が DOM で取れる。**配信者の投稿は `owner`、他の視聴者は空文字 |
| ③ タイムスタンプ(DOM) | `#timestamp` のテキストは **`3:46 PM` 形式**(時計の絶対時刻だが**分単位・日付なし**) |
| ③ タイムスタンプ(Polymer) | µs の絶対 epoch が取れる |
| バッジ | `type` / `aria-label` を持つバッジは**採れていない**(初回は中身の `span` を拾っていた。プローブ側を修正済み) |

### 結論 — **DOM だけでは投稿者を特定できない**

上の「読み方」の表でいう **「`—`(Polymer にはある)」の行**に落ちた。しかも②も外れており、
**塞ぐべき穴が 2 つある。**

1. ~~**ワールドの壁**~~ → **解消した(下の 4.)。** チャンネル ID は DOM 属性からも取れるので、
   メインワールドへの注入は要らない。以下は初回採取時点の記述として残す:
   ~~チャンネル ID はページの JS が要素に載せたプロパティにしか無く、隔離ワールドからは読めない~~
2. **鍵の形(未決着)** — 取れたのは `UC…` で、**辞書の鍵(`@handle`)と文字列比較で一致しない。**
   `findEntry` は正規化済み URL の一致で照合するので、このままでは永久に空振りする。
   → ただし **③ を参照。ハンドルが内部データに無いとはまだ言えない。**

3. **ハンドルは内部データにも無い(2026-08-15 の再採取で確定)**
   初回はキー名(`channel` / `author.*id` / `externalId`)で絞っていて
   `canonicalBaseUrl` のようなキーを見ていなかったため、**キー名に頼らず
   `@ハンドル` らしい値を全部拾う**探索を足して採り直した。結果、一致したのは
   **`authorName.simpleText` の 1 件だけ。**
   - ⚠️ **これは表示名であってハンドルではない。**チャンネル名は誰でも自由に決められるので、
     形が `@…` でも「その人のハンドル」である保証がない。**これを鍵にするのは
     spec.md D1 (a)(表示名照合)そのもの**であり、同名の別人・改名・なりすましで
     **別人のリンクを貼る**
   - したがって **`UC…` と辞書の鍵(`@handle`)をつなぐ対応付け(D1 c)が要る**

### 4. ✅ **DOM 属性に投稿者が入っていた**(2026-08-15 に Elements で発見 → **実配信で検証済み**)

`①` の「DOM からは取れない」は**私の探し方の問題だった可能性が高い。**
メッセージ要素の **DOM 属性** `whole-message-clickable` に
`liveChatItemContextMenuEndpoint.params` が入っており、**base64 を 2 回**解くと protobuf が出る。

```
params → base64 → base64 → protobuf
  ├ メッセージ ID
  ├ { チャンネルID, 動画ID }   ← 動画とセット = 配信の持ち主
  └ { チャンネルID }           ← 投稿者
```

初回の探索が当たらなかったのは、**属性値の中で `UC…` が base64 に埋もれていて
そのままの文字列としては現れない**ため(`attrHits` は生の `UC` / `@` を探していた)。

- **DOM 属性なので content script(隔離ワールド)から読める** → **メインワールド注入が要らなくなる**
- ただし取れるのは `UC…` のままなので、**②(ハンドルとの対応付け)は変わらず必要**
- ⚠️ **これは公開された仕様ではない。**フィールド番号・順序が変われば壊れる。
  そのため**「2 つ目を採る」のような位置頼みにしない** — **動画 ID と隣り合っているほうを
  配信の持ち主として除外**する(`v=` と突き合わせられるので、位置が変わっても効く)。
  切り分けられなければ**投稿者は取れなかったものとして扱う**(推測しない)

**検証結果 (2026-08-15 / 実配信)**: DOM 属性から取り出した ID を、Polymer の
`authorExternalChannelId`(正解)と 1 件ずつ突き合わせた。
**通常のテキストメッセージは全件「一致」。**取れなかったのは
`yt-live-chat-viewer-engagement-message-renderer`(システムメッセージ)だけで、
これは投稿者が存在しないので正常。**UC は毎回ちょうど 2 個**(持ち主 + 投稿者)だった。

> **したがって①は DOM だけで解ける。メインワールドへの注入は要らない。**
> D1 で 2026-08-14 に「注入を許す」と決めたが、**その前提は消えた**(注入せずに済むなら
> そのほうが注入範囲が広がらない)。**②(対応付け)は変わらず必要。**

### ついでに確定したこと(D2 の材料 / `YTRP.watch` より)

- **Polymer の µs 時刻は本物の絶対時刻** — 追加された瞬間との差が 0 秒だった。
  **AC9(監視開始より前のコメントに反応しない)を秒単位で切れる**
- **`author-type="owner"` は追加ノードにも付く** — **AC10 の歯止め 3 枚目は成立する**
- どちらも**メインワールド側**の話ではなく `author-type` は DOM 属性なので、
  **3 枚目だけは壁を越えずに実装できる**(時刻のほうは Polymer 側 = 壁の内側)

**D1 は「(a) 表示名照合」と「(c) 対応付け」の二択ではなく、
「メインワールド注入を許すか」がその手前に立つ。**判断は人間が行う(spec.md D1 / plan.md R1)。

> **決定(2026-08-14 / 人間): メインワールド注入を許す。**
> `authorExternalChannelId` を読むために `world: "MAIN"` の読み取り専用スクリプトを足す方向。
> **対応付け(D1 c)が要るかどうかは、上の③の再採取で決まる。**

### D2 側の材料

- **自分(配信者)の判別は成立しうる** — `author-type="owner"` が **DOM 属性**で取れるので、
  AC10 の歯止め 3 枚目は**ワールドの壁を越えずに**実装できる
- **AC9 のタイムスタンプは DOM だけだと弱い** — `3:46 PM` は**分単位で日付が無い**ため、
  「監視を張った時刻より前か」を秒単位で切れない(同じ分に現れたコメントを区別できない)。
  µs の絶対時刻は Polymer 側にあり、①と同じ壁の内側

### 採取そのものについて分かったこと(プローブの修正点)

- **`YTRP.probe()` の戻り値をコンソールが展開すると、匿名化を素通りして生のチャンネル ID が出る。**
  戻り値を匿名化済みの表に変えた
- **`copy()`(DevTools のコマンドラインAPI)は studio.youtube.com で使えなかった**
  (`copy is not a function`)。`YTRP.show()` を足して `console.log` で出す形にした
