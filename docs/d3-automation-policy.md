# D3 リサーチ — 自動投稿は規約に触れるか

spec.md の「降りる箇所」D3 の判断材料。**本文(§結論の要約〜§未確定のまま残ること)は調査だけで、判断はしていない。**
調査日 2026-08-06(§7 の追加調査 2026-08-17 / §8 の追加調査 2026-08-22)。

**判断の記録は末尾の「判断の履歴」にある**(001 の決着 / 004 での再判断 / 配布経路の切り替え)。

## 結論の要約

| 論点 | 分かったこと |
|---|---|
| YouTube 利用規約 | 「自動化された手段(ロボット、ボットネット、スクレーパなど)を使用して本サービスにアクセスすること」を禁止。**文言上は当たりうる。**適用範囲を限定する但し書きは検索エンジンと書面許可のみ |
| YouTube スパムポリシー | 禁止対象は「大量の、反復的な、誤解を招くコメント/チャットでトラフィックを誘導」。**本機能の投稿頻度・内容は想定されている像から遠い** |
| 公式 API の存在 | チャットへの**投稿は公式 API (`liveChatMessages.insert`) で明示的に認められている**。Nightbot 等はこれを使い、YouTube から増枠まで受けている。**「配信者のチャットにボットが投稿すること」自体は YouTube の想定内** |
| 固定 (ピン留め) | API が無い。DOM 操作以外に手段がない |
| Chrome ウェブストア | **第三者サービスの規約順守を求める条項は見つからなかった。**同種の拡張(YouTube のコメント自動返信等)が現に掲載されている |
| 摘発の前例 | **DOM 操作でチャットに投稿した拡張・配信者が処分された事例は見つからなかった。**「安全である証拠」ではなく「証拠が無い」 |
| 同種ツールの不在(§7 / 2026-08-17 追加) | **規約が原因という証拠は出なかった。**投稿だけの拡張・ボットは現に多数ある。**無いのは固定で、これは公式 API にメソッドが存在しないため**(Streamer.bot でも未実装) |
| 配布経路の選択肢(§8 / 2026-08-22 追加) | ウェブストアには**限定公開 (Unlisted)** がある。**審査は公開と同じ**なので §5 は変わらないが、**発見性が無く・署名され・自動更新が効く。「出す / 出さない」の二択ではない** |

## 詳細

### 1. YouTube 利用規約の文言

[利用規約](https://www.youtube.com/t/terms?hl=ja)「サービスの利用に関する制限」より:

> 自動化された手段(ロボット、ボットネット、スクレーパなど)を使用して本サービスにアクセスすること
> (a) 公開されている検索エンジンを YouTube の robots.txt ファイルに従って使用する場合、または
> (b) YouTube が事前に書面で許可している場合を除く

- **禁止されているのは「アクセス」**であって「投稿」と書かれてはいない。ただし例示 (ロボット/スクレーパ) は
  クローラを念頭に置いた書き方で、**この拡張のような「人が開いた画面上で人の代わりに操作する」形が
  含まれるかは、文言からは決まらない**。
- 「本サービスの一部の改変・修正」の禁止もある。**DOM を書き換えるのではなく、
  人と同じ操作 (入力欄に文字を入れて送信、メニューから固定を選ぶ) をしているだけ**なので、
  こちらは当たりにくいと読める。
- **どちらも読みであって、YouTube の見解ではない。**

### 2. スパムポリシー

[スパムと欺瞞行為のポリシー](https://support.google.com/youtube/answer/2801973?hl=ja) が禁じているのは:

- 大量の、反復的な、または誤解を招くコメント/チャットでトラフィックを誘導すること
- 自動化ツールや AI で類似コンテンツを最小限の変更で大量生産すること
- コミュニティ機能を悪用したエンゲージメントの強制

本機能は **リダイレクトを受け取ったときにだけ・1 送信元につき 1 回 (既定クールダウン 6 時間)・
人間可読の返礼文・誘導先は相手のチャンネル**。**ポリシーが撃とうとしている像とは形が違う。**
ただし「送信元チャンネルへのトラフィック誘導」という一点だけを切り出せば字面は重なる。

### 3. いちばん効く材料 — 公式 API で投稿は認められている

- チャットへの投稿には公式 API [`liveChatMessages.insert`](https://developers.google.com/youtube/v3/live/docs/liveChatMessages) がある。
- Nightbot / Streamlabs 等の**チャットボットはこれを使って自動投稿しており、
  YouTube はそれらに API クォータの増枠まで与えている**。
- つまり **「配信者のライブチャットにプログラムが自動で投稿する」という行為そのものは、
  YouTube が正面から用意している機能**である。争点は行為の中身ではなく **経路** (API か DOM か) に絞られる。

これは D3 の重心を大きく動かす。「自動投稿してよいか」ではなく
**「認められている行為を、認められた経路以外でやることをどう見るか」**が実際の論点。

### 4. 固定 (ピン留め) には経路が無い

固定の API は存在しない (spec.md の前提どおり)。**経路の選択肢がそもそも無い**ため、
「API で代替できるのにわざわざ DOM を叩いている」という批判は固定については成立しない。

**一次情報で確認済み (2026-08-17)。** [`liveChatMessages`](https://developers.google.com/youtube/v3/live/docs/liveChatMessages) の
メソッドは `list` / `streamList` / `insert` / `transition` / `delete` の 5 つで、**pin / unpin は無い。**

### 5. Chrome ウェブストア側

- [プログラムポリシー](https://developer.chrome.com/docs/webstore/program-policies) に
  **第三者サービスの規約順守を求める明文は見つからなかった。**
  審査で見るのは単一用途・権限の妥当性・データの扱い・機能の説明との一致。
- 「非自明な機能を含めない / 利用者に驚きを与えない」という条項はある。
  **自動投稿は掲載文と設定画面で明示しているので、これは満たしている。**
- 同種の拡張(YouTube のコメント自動返信、チャット操作系)は現に掲載されている。
- ただし**ストアは権利者からの申立てで削除する**。YouTube が動けば掲載は消える。
  審査を通ることと、後で消されないことは別。

### 6. 実際に賭けているもの

| 誰の | 何が | 大きさ |
|---|---|---|
| 自分 | YouTube チャンネル | **これが一番重い。**配信者にとってチャンネル停止は事業の停止 |
| 配布先の他人 | その人のチャンネル | 自分では引き受けられないリスクを他人に負わせる形になる |
| 開発者アカウント | ストアの掲載・デベロッパー登録 | 消えても作り直せる |

**ストアに出すとは「3 番目のリスクを取る」ことではなく「2 番目のリスクを他人に負わせる」こと。**
D3 の重さはここにある。

### 7. 同種のツールが存在しないのはなぜか (追加調査 2026-08-17)

「この類の拡張が出ていないのは規約が理由か」を確かめた。**規約が原因という証拠は出なかった。**

| 見たこと | 分かったこと |
|---|---|
| 公式 API の固定 | **無い**(§4 に一次情報を追記)。争点ではなく単なる不在 |
| Streamer.bot | 「YouTube ライブチャットの固定/固定解除を自動化してほしい」という [feature request](https://ideas.streamer.bot/posts/1326/feature-request-youtube-live-chat-pin-functionality-for-streamer-bot) が立っており**未実装**。一方で [`Send Message to Channel`](https://docs.streamer.bot/api/sub-actions/youtube/send-message-to-channel) は**ある** → **投稿はできる・固定だけできない**という非対称が業界の標準状態 |
| 自動投稿する拡張のストア掲載 | [Youtube comments responder](https://chromewebstore.google.com/detail/youtube-comments-responde/ifkackeifeaagecangmbcpkpniopcnfj) / [YouTube AI Reply](https://chromewebstore.google.com/detail/youtube-ai-reply/hmjcbogknejpjbhdeimejebenlbhcbpb) が現に掲載されている → **ストアが「YouTube への自動投稿」を弾いている形跡は無い**(§5 と一致)。**ただしどちらも通常コメントへの返信でライブチャットではなく、経路が API か DOM かも未確認** |
| ライブチャットの DOM を触る前例 | [Chat Fusion](https://github.com/UrbinCedric/Chat-Fusion) がコンテンツスクリプト + MutationObserver でライブチャットの DOM を監視。**ただし読み取り専用で投稿はせず、ストアにも出していない**(デベロッパーモード読み込み) → **「ライブチャットへ DOM 経由で投稿する」前例としては使えない** |
| 用途そのもの | 「リダイレクト受信 → 返礼投稿 → 固定」を扱うツール・拡張・記事は**日本語でも英語でも 1 件も見つからなかった**(出るのは YouTube 公式のリダイレクト説明のみ) |
| 摘発の前例 | **再調査でも見つからなかった**(§未確定のまま残ること と同じ状態) |

**読み: 同種ツールが無い理由は、重い順に (1) 固定に公式の経路が無い (2) DOM 依存の保守コスト (3) 用途の母数が小さい。
規約は「作らせない理由」としてではなく「事後に効くリスク」として働いている。**
これは D3 の判断を動かすものではない — **経路 (§3) が論点であることは変わらない**が、
「グレーだから誰も出していない」という読みは**支持されなかった**。

**この調査の限界:** ウェブ検索 6 件 + API ドキュメント 1 件。**ウェブストアの全文検索・GitHub のコード検索は掛けていない**ため、
埋もれた個人プロジェクトは見落としうる。Streamer.bot の feature request も**本文のみ確認でコメント欄は取得できず**、
「API が無いから未実装」と運営が明言しているかは未確認。

### 8. 配布経路の選択肢 — ストアの「限定公開」 (追加調査 2026-08-22)

001 は「ストアに出す / 出さない」の二択で決着したが、**ウェブストアの公開範囲は 3 段階ある**
([Distribution タブ](https://developer.chrome.com/docs/webstore/cws-dashboard-distribution))。
**限定公開・非公開は 001 / 004 のどちらの検討にも出てきていない。**

| 公開範囲 | 一次情報の記述 |
|---|---|
| 公開 (Public) | ストアの検索・カテゴリ一覧に出る |
| **限定公開 (Unlisted)** | 「ストア上にリスティングを作らないが、**ウェブストアの URL を知っていれば誰でもインストールできる**」。検索・一覧には出ない |
| 非公開 (Private) | 指定したユーザー(トラステッドテスター / Google グループ)だけがインストールできる。公開前テスト向け |

**分かったこと:**

- **審査は 3 つとも同じ。**限定公開でも免除されない([審査プロセス](https://developer.chrome.com/docs/webstore/review-process))。
  → **§5 の「審査は YouTube の規約を見ない」は限定公開でも同じ。**
  「通った＝セーフ」という誤解は公開範囲では消えず、**消すなら掲載文で開示するしかない**(README と同じ文面を置けば足りる)。
- **発見性は無い。**ストア検索・カテゴリから拾われる経路が塞がるので、
  **§6 で重く見た「事情を知らない他人にリスクを負わせる」形にはならない。**
  到達経路は README のリンク経由に固定され、**現状の GitHub Releases 配布と実質同じ。**
- **署名され、ストア配布になるので自動更新が効く。**
  現状の未署名 ZIP は**自動更新されない**([install.md](install.md#未署名であることの影響))。
  → **送信元の取り違え([t1-findings.md](t1-findings.md) の 2 件)の修正を出しても、古い版を使い続ける人が残る**
  という現状の弱点が消える。
- **代わりに失うのは「デベロッパーモード読み込み」という摩擦。**
  001 が実際にフィルタとして効かせていたのはこれ(開示ではなく手順の面倒さ)。
  ただし**「手順を踏める人」＝「規約リスクを判断できる人」ではない**ので、代理指標としては粗い。

**要るもの / 残るリスク:**

- 開発者登録 **$5(一度きり)** と本人確認。
- **プライバシータブの申告は限定公開でも必須。**2026-08-01 から運用が強化されている
  ([2026 のポリシー更新](https://developer.chrome.com/blog/cws-policy-updates-2026))。
  本拡張は保存が全部ローカル([privacy-policy.md](privacy-policy.md))なので申告自体は軽いはずだが、
  審査での挙動との突き合わせは以前より厳しい。
- **単一用途ポリシー。**引き金が 2 種類(リダイレクト受信 / 登録者のコメント)あるため、
  2 機能と見なされる可能性はある。**弾かれる想定ではないが、通る保証も無い。**
- **YouTube からの申立てで掲載が消えるのは公開範囲に関係なく同じ**(§5)。
  消えても既存インストールが即死ぬわけではないが、更新は止まる。
- **2026 のポリシー更新にも、第三者サービスの規約順守を求める条項は追加されていない。**
  → **§5 の調査結果は 2026-08-22 時点でも有効。**

**この案が動かすもの / 動かさないもの:**

**規約リスク(§1〜§4 の「経路」の論点)は 1 ミリも動かない。**動くのは**配布の摩擦と、修正の届き方**だけ。
つまりこれは D3 の規約論点の答えではなく、**「出さない」の理由のうち §6(他人にリスクを負わせる)にだけ効く案。**

**この調査の限界:** 公式ドキュメントの読解のみで、**実際に申請していないので審査を通るかは未確認。**
非公開(テスター指定)の人数上限は**公式ドキュメントに明記が見つからなかった。**

→ **判断済み (2026-08-23)**(→ 末尾「判断の履歴」の「配布経路の切り替え — 限定公開へ」)。

## 取りうる形

### A. 現状のまま (自動検知 → 自動投稿 → 自動固定、既定 ON)

価値は最大。spec.md の「配信者は何もしない」を満たす唯一の形。
規約リスクを配布先にそのまま渡す。

### B. 自動を既定 OFF にして、手動トリガーを既定の経路にする

チャット右下の「↩ 返礼」は既に実装済み。**人の 1 クリックを起点にすれば
「自動化された手段によるアクセス」からは一段遠い。**
掲載文・オプション画面で「自動投稿を有効にするとどうなるか」を明示し、本人に選ばせる。
自分の配信では ON にすればよく、**自分が失う価値はほぼ無い。**
→ **配布を前提にするならこれが素直。**

### C. 投稿だけ公式 API・固定だけ DOM

- 投稿を `liveChatMessages.insert` に置き換えれば、**行為の大半が公式に認められた経路になる。**
- コスト: OAuth が要る。YouTube のスコープは Google の分類で **sensitive**
  (restricted ではない) なので、**アプリ審査 + デモ動画は要るが、第三者セキュリティ評価までは不要**
  ([sensitive scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification))。
  未審査でもテストユーザー 100 人までは動くので、**自分＋知人配布なら審査無しで足りる。**
- クォータ: 既定 10,000 単位/日、insert は 50 単位 → **1 日 200 通。**本用途には十二分。
- ただし実装量は増える (OAuth フロー、トークン保管、配信 ID と liveChatId の解決)。
  **固定は結局 DOM なので、リスクをゼロにはできない。**

## 未確定のまま残ること

- YouTube が「ブラウザ拡張による代行操作」を規約上の自動化アクセスとみなすかどうか。
  **公式見解は見つからなかった。**
- この形での処分の前例。**見つからなかった (無いことの証明ではない)。2026-08-17 の再調査でも同じ。**
- ストアに出した後、YouTube 側から申立てが来る確率。**推し量る材料が無い。**

## 判断の履歴

### 001 — 初回の決着(前提: 引き金はリダイレクト受信の 1 種類のみ)

上の調査を踏まえ、**「グレーだが、開示した上で自己責任」**で決着した
([001 spec.md](../specs/001-redirect-pin/spec.md) D3)。決めたのは 3 点:

- **Chrome ウェブストアには出さない。** 審査は YouTube の規約に触れるかを見ないため
  「通った」が誤った安心になり、事情を知らない人にリスクを負わせることになる
- **GitHub でグレーな点を全部開示した上で配布し、判断できる人が自己責任で使う**
- **「有効にする」は自動投稿だけを止めるスイッチにし、手動トリガーは通す**(001 AC7)。
  書き込みを人の操作だけに限る使い方を成立させるため

**採ったのは上の「取りうる形」 A(自動検知・自動投稿・自動固定)に、開示と配布経路の限定を付けた形。**
**B(自動を既定 OFF にして手動トリガーを既定の経路にする)は採っていない** —
`enabled` の既定は `true`([src/config.ts](../src/config.ts))で、既定 OFF なのは
`showManualTrigger`(security-review S8: 配信画面への映り込み対策)のほう。**ここを取り違えない。**

**B(§取りうる形で「配布を前提にするならこれが素直」と書いた案)を採らなかった理由:**
手動トリガーを既定の経路にすると、**001 の目的「配信中は手が離せないので配信者は何もしない」が成立しない**
([001 spec.md](../specs/001-redirect-pin/spec.md) のユーザーストーリー)。
B が素直なのは**配布を前提にした場合**で、001 は**ウェブストアに出さない**ことを同時に決めたため、
「素直さ」が効く前提のほうを外した。代わりに**開示と配布経路の限定**でリスクを引き受ける形にしている。

### 004 — 再判断(2026-08-13 / 人間 / [004 spec.md](../specs/004-comment-link/spec.md) D3・T11 #35)

**何が変わったか:** [004](../specs/004-comment-link/spec.md) が
**自動投稿の引き金を 1 種類から 2 種類に増やす**(リダイレクト受信 + 登録した人のコメント)。
コメントはリダイレクトより桁違いに多いので、**ON にしたときの投稿頻度が上がる。**
001 の結論は「リダイレクト受信時のみ・低頻度」を前提にしていたため、**前提が変わった。**

**結論: 001 の判断を維持する。** 004 を理由に方針を変えない。

理由:

1. **配布先が負うリスクは増えない。** `commentReplyEnabled` は**既定 OFF**、
   辞書側の「コメントに反応する」フラグも**既定 false**(リダイレクト受信による自動登録でも false)。
   **利用者が明示的に 2 つ ON にしない限り、挙動は 001 と同じ。**
   001 本体は既定 ON のまま(上記)だが、**004 が足す引き金には B の考え方(本人に選ばせる)を適用した**
   — 頻度が上がる側の引き金だけを既定 OFF にしたので、**既存の利用者が黙って頻度の高い側へ動くことはない。**
2. **ON にしたときの頻度も、スパムポリシーが撃とうとしている像から遠い。**
   1 配信・1 人につき 1 回 / 最低 5 秒間隔 / 1 配信 20 件の上限 / 誘導先は相手のチャンネル /
   文面は人間可読。「大量の、反復的な、誤解を招く」に寄る形にはしていない。
3. **争点は 001 と同じく経路(公式 API か DOM か)。** 引き金が 1 つ増えることは、
   §3 で整理した「認められている行為を、認められた経路以外でやること」という論点を動かさない。

**あわせて決めたこと:**

- **頻度を抑える設計は据え置き。緩めない。** 既定 OFF / 1 配信 1 人 1 回 / 5 秒間隔 / 20 件上限は
  004 の受け入れ条件(AC1・AC7・AC11)として固定する。**運用で緩めたくなったらこの判断からやり直す。**
- **経路を公式 API(`liveChatMessages.insert`)へ寄せる案(§C)は引き続き未採用。**
  004 のスコープ外。必要になったら別 feature として起こす。
- **開示は 004 の T10 が持つ。** README / install.md / 公開ページに
  **引き金が増えたこと・既定 OFF であること**を書く。
  → **反映済み (2026-08-16 / T10)。** README / [install.md](install.md) / [index.html](index.html) /
  [for-testers.md](for-testers.md) と**配布 ZIP の `INSTALL.txt`** に、
  **引き金が 2 種類になったこと・既定 OFF(スイッチと辞書のフラグの両方)・
  ON にすると頻度が上がること・歯止め(1 配信 1 人 1 回 / 5 秒間隔 / 20 件上限)**を書いた。
  あわせて **D5 の決定に基づき「実配信での通し確認は未実施」を明記**した(T12 が済んだら外す)。

### 配布経路の切り替え — 限定公開へ(2026-08-23 / 人間 / §8)

**決着した。ウェブストアの「限定公開 (Unlisted)」へ切り替える。**
現状の「未署名 ZIP + デベロッパーモード読み込み」をやめ、ストア経由の配布に移す。

**決め手は §8 の 2 行:**

- **発見性が無い**ので、§6 で重く見た「事情を知らない他人にリスクを負わせる」形にはならない。
  到達経路は README / 説明ページのリンクだけで、**現状の GitHub Releases 配布と実質同じ。**
  001 が「出さない」を選んだ理由のうち、ここだけが限定公開で消える。
- **署名され、自動更新が効く。**現状の未署名 ZIP は自動更新されないため、
  **送信元の取り違え([t1-findings.md](t1-findings.md) の 2 件)の修正を出しても、
  古い版を使い続ける人が残る。**これが消える。この一点が今回いちばん効く変化。

**引き換えに失うのは「デベロッパーモード読み込み」という摩擦。**
001 が実際にフィルタとして効かせていたのはこれ(開示ではなく手順の面倒さ)だが、
**「手順を踏める人」＝「規約リスクを判断できる人」ではない**ので、代理指標としては元から粗い。
**摩擦の代わりは掲載文の開示に置く**(下記)。

#### 何を決めていないか — ここを取り違えない

- **規約の論点(§1〜§4)は 1 ミリも動かない。**争点は経路(公式 API か DOM か)のままで、
  限定公開はそこに何も答えていない。
- **001 の「グレーだが、開示した上で自己責任」は維持する。**配布経路が変わるだけで、
  リスクの引き受け方は変えない。
- **公式 API 経路(§取りうる形 C)は引き続き未採用。**必要になったら別 feature として起こす。
- **「審査を通った = セーフ」ではない。**審査は公開・限定公開・非公開のどれでも同じで、
  **YouTube の規約に触れるかは審査対象外**(§5)。公開範囲を絞っても誤解は消えないので、
  **消すなら掲載文で開示するしかない。**README の警告と同じ趣旨をストアの掲載文にも置く。
- **YouTube 側の申立てで掲載が消えうる**のは公開範囲に関係なく同じ(§5)。

#### あわせて決めたこと

- **配布は掲載後にストアへ一本化する。**掲載が通った時点で、**新しい版を GitHub Releases へ出すのをやめる。**
  過去の Release は**消さない**(既に落として使っている人のリンクを壊さないため)。
  2 経路を並走させない理由は手間ではなく**二重投稿**で、ストア版は拡張 ID が変わりうるため
  Chrome の「同じ ID の拡張機能が既にあります」という重複防止が効かなくなる。
  **旧版とストア版が同時に有効になると、同じ相手へ 2 回投稿する。**
- **限定公開の URL は、いま ZIP のリンクが載っている 4 か所に置く。**
  README / [説明ページ](index.html) / [install.md](install.md) / [for-testers.md](for-testers.md)。
  新しい到達経路は作らない。
- **移行手順の先頭は「先にデベロッパーモードの旧版を削除する」。**
  拡張 ID と設定の引き継ぎをどう扱うかは**まだ決まっていない**(別タスク)。
  設定・辞書・投稿履歴が引き継がれるかは、そこが決まるまで**断定して書かない。**

#### 「見るタイミング」との食い違いについて

§8 を書いた時点では、**T12(実配信での通し確認)が済んで「ほとんど検証されていない」という
もう一方の理由が薄れたときに天秤をかけ直す**としていた。**T12 はまだ済んでいない。**

判断を先に記録したのは、**リポジトリが「ストアには出さないと決めました」と明記した状態のまま
提出作業を進めると、書いてあることとやっていることが食い違う**ため。
**実配信での通し確認は、提出の前提として残す** — 済んでいない状態で提出はしない。
README / 説明ページ / 掲載文の「実配信での通し確認は未実施」という但し書きも、
**T12 が済むまで外さない。**

#### 反映するところ

- **README の「⚠️ 使う前に読んでください」** — 「出さない」という結論だけを差し替える。
  **理由の中身(審査は YouTube の規約を見ない / 通った事実が誤った安心になる)は消さない。**
- **[001 spec.md](../specs/001-redirect-pin/spec.md) の D3** — 決定 3 点のうち
  「ウェブストアには出さない」が変わる。
- **配布経路そのものの差し替え(README の入れかた / install.md / index.html / for-testers.md /
  配布 ZIP の `INSTALL.txt` / CHANGELOG)は掲載が通ってから。**掲載前に書き換えると、
  存在しない URL を案内することになる。
