## 目的

日本語以外の環境でもこの拡張を使えるようにする。**UI の言語**と、**検知が依存している
YouTube 側の文言**は別の問題なので、分けて扱う。

## 背景 / 課題

現状は**日本語専用**。しかもその依存が 2 層に分かれている。

### ① 自分たちの UI(翻訳すれば済む)

manifest の名前・説明、オプションページ、手動トリガー「↩ 返礼」パネル、コンソールログ。
`public/options.html` の日本語行が約 55、TS 側の日本語文字列が約 30。
**MV3 標準の `_locales/` + `chrome.i18n` で片付く。**

### ② 検知が見ている YouTube 側の文言(翻訳では済まない)

`src/selectors.ts` は、YouTube が画面に出す**日本語そのもの**を照合している。

| 定数 | 用途 | 影響 |
|---|---|---|
| `REDIRECT_TEXT_PATTERNS` | リダイレクト受信の検知 | 当たらないと**①が動かない** |
| `EXCLUDED_TEXT_PATTERNS` | 送信側バナーの誤爆よけ | 外すと**逆向きに投稿する**(2026-08-06 の事故 2 件目) |
| `PIN_MENU_LABELS` / `UNPIN_MENU_LABELS` | 「固定」メニューの特定 | 当たらないと**③が動かない** |

**これらは翻訳する対象ではなく、各言語で実際に何と表示されるかを採取する対象。**
さらに採取の難度が違う:

- **メニューのラベル**は、その言語で Studio を開いてメニューを開けば読める → **誰でも採取できる**
- **通知の文言**は、その言語設定で**実際にリダイレクトを受けないと出てこない** → **手元では作れない**

つまり ② は実装課題ではなく **データ収集課題**。集める導線(Issue テンプレの
「Studio の表示言語」「リダイレクト通知の文面」欄)は 001 で既にできている。

## スコープ

- **含む**:
  - `_locales/` + `chrome.i18n` による UI の多言語化(既定 `ja` / 追加 `en`)
  - `src/selectors.ts` の文言テーブルを**言語をまたいで持てる形**にする
  - 英語 UI の `PIN_MENU_LABELS` / `UNPIN_MENU_LABELS` を実採取して確定させる
  - 報告された通知文言を安全に取り込む導線(未確認→確認済みの昇格)
- **含まない**:
  - **英語以外の言語**(データが来てから別 feature か、本 feature の追加タスクで足す)
  - 英語圏での自動検知の動作保証(通知文言の実データが無いため約束できない)
  - ドキュメント(README / GitHub Pages / install.md)の英訳 → 別 feature

## 受け入れ条件

| # | 条件 |
|---|---|
| AC1 | オプションページ・手動トリガー・manifest の名前/説明が、**ブラウザの言語設定に従って** `ja` / `en` で表示される |
| AC2 | 既定ロケールは `ja`。**未知の言語では `en` に落ちる**(空文字やキー名が出ない) |
| AC3 | 文言テーブルが言語ごとに分かれていて、**言語を 1 つ足すのがテーブルへの追記だけで済む** |
| AC4 | 英語 UI の Studio で、**「固定」メニューが特定できる**(実採取したラベルで) |
| AC5 | **未確認の文言が自動投稿の本線に入らない。** 推測は診断ログに出るだけで、確認できたものだけが昇格する |
| AC6 | 日本語環境の挙動が**現状から変わらない**(既存テストが通り、文言照合の結果が同じ) |

## メモ / 降りる箇所

- **D1: 未確認の文言を検知の本線に置かない。**
  2026-08-06 に、推測セレクタが文言チェックを飛ばす経路に置かれていたため、
  他人の配信・逆向きのバナーに反応する事故が起きた
  ([t1-findings.md](../../docs/t1-findings.md))。
  **他言語のパターンは既定で `UNCONFIRMED_*` 側に置き、実データで確認できたものだけ昇格させる。**
  この昇格の判断は人間が行う。エージェントに代行させない。

- **D2: 英語圏での「動く」を約束するか。**
  通知文言が未確認のまま `en` UI を出すと、「英語対応」と読まれて自動検知が
  空振りする。**UI だけ英語化して、検知は日本語 UI 前提であることを明示する**のか、
  データが揃うまで `en` 自体を出さないのか。**判断は人間が行う。**

- **D3: 対応言語の広げ方。**
  英語の次にどこを狙うか(そもそも狙うか)は、Issue に来た報告を見てから決める。
  先回りして推測パターンを積まない(D1 に反する)。

- **D4: ドキュメントの英訳をどこまでやるか。**
  UI だけ英語で README と説明ページが日本語のままだと、入れた人が
  **リスク開示を読めない。**「リスクを自分で判断できる人が自己責任で使う」という
  配布方針([README](../../README.md))と噛み合わない。
  **UI の英語化と、少なくとも警告部分の英訳はセットにすべきか**を決める必要がある。
