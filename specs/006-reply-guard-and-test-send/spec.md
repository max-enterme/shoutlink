# 006 返礼の抑止を配信単位に統一し、テスト送信の導線を作る

> spec.md — フィーチャーの「何を・なぜ」。正本はこのテキストと GitHub(Feature issue)。

## 目的

配信者が **「設定したとおりに投稿されるか」を、相手が来るのを待たずに何度でも確かめられる**ようにする。
あわせて、二重になっている再投稿の抑止を **「同じ配信・同じ相手に 1 回」へ一本化**し、
秒数のクールダウンという概念を無くす。

## 背景 / 課題

**① 抑止の規則が 2 つ並走している。**
リダイレクト返礼は `cooldownSec`(既定 6 時間)の時間クールダウン([dedupe.ts](../../src/dedupe.ts))、
コメント返しは「同じ配信で 1 回」([post-log.ts](../../src/post-log.ts) の `findCommentReplyBlocker`)で、
**判定の仕組みが別**。設定画面の「クールダウン」欄はリダイレクト側にしか効かないのに、
そう書いていない(`public/options.html`)。004 の AC7 は既に
「`cooldownSec = 0` を抑止の逃げ道にする運用を持ち込まない」と決めており、
**時間クールダウンは片側にだけ残った旧い仕組み**になっている。

**② 抑止を解く唯一の手段が効いていない。**
設定画面の「履歴を消す」は、開いているチャットのタブに届かない。
`postLog` は [main.ts:65](../../src/main.ts) で起動時に一度読むだけで storage の変更を購読しておらず
(config は `onConfigChanged`、辞書は `onDirectoryChanged` で購読しているのに、履歴だけ入っていない)、
**再読み込みするまで挙動が変わらない。**しかも次に投稿が起きた時点で `rememberPost` が
古い in-memory の配列ごと storage へ書き戻すので、**消した履歴が復活する。**
リダイレクト側の `dedupe` は起動時に履歴から初期化した後 in-memory の `lastFiredAt` だけで
判定する([main.ts:143](../../src/main.ts))ため、storage を空にしても止まったまま。

**③ 設定を確かめる手段が「本番を待つ」しかない。**
今テストできるのは「クールダウンを 0 にして本物のリダイレクトを待つ」だけで、
コメント返しには最初から効かない。手動トリガーは `enabled` を素通りする
([config.ts](../../src/config.ts) の `isActionAllowed`)のに `dedupe.tryAcquire` には例外が無いので、
**既定 6 時間だと同じ相手を 6 時間に 1 回しか試せない。**
[self-echo.ts](../../src/self-echo.ts) が「そこは配信者が調整する値であって、自己ループの歯止めを
預けてよい場所ではない」と書いているとおり、**設定値をテストの逃げ道に使う運用そのものを畳みたい。**

③ の導線ができることで ① の統一が可能になる、という関係にある。3 つは 1 本の feature。

## スコープ

- **含む**:
  - 辞書の行ごとの**テスト送信**(設定画面 → 開いているライブチャットのタブへ実投稿)
  - **「履歴を消す」がチャットのタブへ届く**ようにする(再読み込み不要)
  - `cooldownSec` の廃止と、リダイレクト返礼の抑止の**「同じ配信・同じ相手に 1 回」への統一**
  - 手動トリガーを抑止の対象外にする
  - 上記に伴う README / `docs/` / 設定画面の説明の書き換え
- **含まない**:
  - コメント返しの **004 / AC9**(監視開始時点で既にあるコメントに反応しない)の変更
  - 1 配信 20 件の上限・最低間隔 5 秒([post-queue.ts](../../src/post-queue.ts))の変更
  - 固定モード・i18n(002)・ストアへの再申請

## 受け入れ条件

### 抑止の統一

- [ ] **AC1** リダイレクト返礼の抑止は **「同じ配信・同じ相手に 1 回」**で判定する。**判定に秒数を使わない。**配信(`streamId`)が変われば再び 1 回投稿する(ただし記録側の配信 ID が空のときは AC2 に従う)。**数えるのは投稿できた回だけ** — 投稿に失敗した回は抑止に数えず、次に検知したときにもう一度試す。
- [ ] **AC2** **問い合わせ側または記録側の `streamId` が空**のときは、**6 時間の窓**(`UNKNOWN_STREAM_WINDOW_SEC`)で判定する。リダイレクト返礼・コメント返しに同じ規則を当てる。**記録側が空の場合、配信が変わっても 6 時間は抑止が効く** — 管制室の埋め込みチャット(配信 ID が取れない)で投稿し、次の配信をポップアウトで開いた場合が該当する。取りこぼしより二重投稿を避ける(004 / AC7 と同じ判断)。
- [ ] **AC3** 004 / AC8 の**非対称は維持する** — 同じ配信でリダイレクト返礼済みならコメント返しはしない。コメント返し済みでもリダイレクト返礼はする。
- [ ] **AC4** 001 の「**チャットを再読み込みしても同じ相手へ再投稿しない**」(2026-08-06 の不具合)が壊れない。リロード後の初期走査が同じ通知を拾い直しても投稿しない。
- [ ] **AC5** 設定から `cooldownSec` が消える。**保存済みの `cooldownSec` が残っていても落ちず**、判定にも使われない(`normalizeConfig` が読み捨てる)。設定画面から「クールダウン」欄が無くなる。
- [ ] **AC6** **手動トリガーは抑止の対象外**。人が押した時点で意思表示なので、同じ配信・同じ相手でも押せば投稿する。`enabled` の扱い(`isActionAllowed`)と揃える。**投稿できた分は履歴に残す**(本番の代替経路であるため)。**ただし同じ相手への投稿がいま走っている間は、手動でも投稿しない** — これは抑止ではなく、チャットの入力欄が 1 つしかないことへの手当て(AC13 と同じ理由)。

### テスト送信

- [ ] **AC7** 設定画面の辞書の**行ごとにテスト送信ができる**。押すと、開いているライブチャットのタブへ、その行の設定で組み立てた文面を**実際に投稿する。**
- [ ] **AC8** テスト送信は**投稿履歴に残さない。**抑止の「1 回」を消費せず、**同じ行を何度でも押せる。**
- [ ] **AC9** 結果が**押した行にその場で返る。**次の **6 つを互いに違う文言で**区別する: **投稿できた**(投稿した文面と、**どの配信へ出したか**も出す) / **投稿に失敗した**(チャットの入力欄が見つからない) / **ライブチャットのタブが開いていない** / **その行はチャンネル ID が未解決**(コメント返し側のみ) / **その行がまだ保存されていない**(チャット側の辞書に無い) / **他の投稿が走っている**。
- [ ] **AC10** テスト送信は「リダイレクトを自動検知して投稿する」「コメントに反応して投稿する」の **ON / OFF に関わらず押せる。**人が明示的に押しているため(手動トリガーと同じ流儀)。
- [ ] **AC11** ⚠ **テスト送信した文面を「自分が投稿した本文」として記憶する**(004 / AC10 の 1・2 枚目)。記憶しないと、テスト送信した文面をコメント経路が拾って返信が走る。**投稿の前に本文を、投稿できてから要素を**登録する(004 / `comment-runner.ts` と同じ順序。逆にすると間に合わない)。**`selfEcho` には登録しない** — 理由は plan.md「採らない案」。
- [ ] **AC12** テスト送信は**固定しない**(004 / AC6 と同じ。固定枠は 1 件しかない)。
- [ ] **AC13** テスト送信は**他の投稿が走っている間は投稿せず**、その旨を返す。**応答が返るまでボタンは押せない**(二度押しで 2 通出さない)。

### 履歴のクリア

- [ ] **AC14** 設定画面で「履歴を消す」を押すと、**開いているライブチャットのタブにも届き、再読み込みなしで抑止が解ける。**あわせて **`selfEcho` の記憶もリセットする** — 消した直後 30 秒だけ同じ相手への自動検知が止まったまま、という状態を残さない。
- [ ] **AC15** 消した後にチャット側が投稿しても、**消える前の履歴が書き戻らない。**

### 壊れないこと / ドキュメント

- [ ] **AC16** 保存内容・受信したメッセージが壊れていても拡張ごと死なない。**未知の形のメッセージは黙って無視する**(004 / AC14 と同じ流儀)。
- [ ] **AC17** README / `docs/` / 設定画面から**「クールダウン(秒数)」の記述が消え**、「同じ配信・同じ相手に 1 回」と**テスト送信の手順**に置き換わっている。`docs/for-testers.md` のテスト手順は、テスト送信を使う形に書き換える。**コード中のコメント・docstring に残る `cooldownSec` / `dedupe` への言及も直す**(消えたものを前提に説明している文が残らない)。**`CHANGELOG.md` は対象外** — 過去のリリースに `cooldownSec` があったことは事実なので書き換えず、今回ぶんの新しいエントリを足すだけにする。

## メモ / 降りる箇所

- **テスト送信の宛先が 1 つに定まるかは実機で確かめる。** `manifest.json` は `all_frames: true` なので、
  `chrome.tabs.sendMessage` を `frameId` 無しで呼ぶと**そのタブの一致する全フレームでリスナーが走る。**
  管制室のタブに `live_chat*` へ一致するフレームが 2 つ以上あると二重投稿になる。
  → 拡張を読み込んだ Chrome で管制室を開き、**DevTools のフレームセレクタに `live_chat` がいくつ出るか**を数える。
  ポップアウトを同時に開いた状態でも見る。2 つ以上出たら、`frameId` を指定する設計に変える判断が要る。
- **AC1 / AC4 の実配信での通し確認は人手。** リロードで再投稿しないことは、実際の配信でリダイレクトを受けないと最終確認ができない(001 の不具合が出た経路そのもの)。ヘッドレスで固められるのは判定の純関数まで。
- **テスト送信は配信中に押すと視聴者に見える。** 「テスト」という名前で実投稿する以上、押し間違いの実害がある。設定画面のどこに置くか(畳んだ行にも出すか)は**モックで確定させる**(→ plan.md「確定値」)。
- **`dedupe.ts` を残すか畳むかはアーキ判断。** `findCommentReplyBlocker` に寄せて 1 本にする案と、`dedupe.ts` の中身だけ入れ替える案がある。001 の抑止を壊すと 2026-08-06 の不具合が戻るので、ここは plan.md で 1 本に決めてから実装に渡す。
