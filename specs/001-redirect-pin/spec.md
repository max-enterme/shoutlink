# 001 リダイレクト検知 → 送信元 URL 投稿 → 固定

## 何を

自分のライブ配信が**他チャンネルからライブリダイレクトを受けた**ことを検知し、
送信元チャンネルの URL を含むメッセージをライブチャットへ投稿し、そのメッセージを固定する。

## なぜ

リダイレクトで流入した視聴者に対して「どこから来たか」の導線を残したい。
配信中は手が離せず、送信元チャンネル名の確認 → URL のコピー → 投稿 → 固定 を手動でやると
確実に取りこぼす。リダイレクトは相手からの厚意なので、返礼の抜けは実害がある。

## ユーザーストーリー

1. 配信中、チャンネル A から自分の配信にリダイレクトが入る
2. 数秒以内に、自分のライブチャットへ
   `Aさんからリダイレクトありがとうございます! https://www.youtube.com/@A` が投稿される
3. その投稿が固定され、以降に流入した視聴者の画面上部に出続ける
4. 配信者は何もしない

## 受け入れ条件

| # | 条件 |
|---|---|
| AC1 | リダイレクト受信から **10 秒以内**にライブチャットへ投稿される |
| AC2 | 投稿文に送信元チャンネルの **URL** と**表示名**が含まれる |
| AC3 | 投稿したメッセージが、**固定モードの設定に従って**固定される(AC8) |
| AC4 | 同一送信元からの多重発火をしない(同一配信内・クールダウン内は 1 回のみ) |
| AC5 | 投稿文が**テンプレートとして編集できる**(`{name}` `{url}` を差し込む) |
| AC6 | 検知・投稿・固定のいずれが失敗しても**配信そのものに影響しない**(例外を握って握りつぶし、ログのみ残す) |
| AC7 | 機能を**その場で無効化できる**(想定外の連投を止められる)。**止まるのは自動投稿だけで、手動トリガーは通す** — 止めたいのは連投であって、人の 1 クリックはそれに当たらない |
| AC8 | **固定モードを設定で指定できる** — `off`(固定しない) / `ifEmpty`(既存の固定が無いときだけ固定・既定) / `always`(既存の固定があっても上書き) |

## 非目標

- 送信側(自分が他チャンネルへリダイレクトする)の自動化
- Twitch / ニコニコ等、YouTube 以外のプラットフォーム
- アーカイブ動画のコメント欄への遡及投稿
- リダイレクト履歴の集計・可視化(将来やるなら別 feature)

## 制約・前提

- **ライブリダイレクトの受信通知は YouTube Data API から取得できない。**
  `liveChatMessage.snippet.type` の enum に raid / redirect 相当の値が無い
  ([リファレンス](https://developers.google.com/youtube/v3/live/docs/liveChatMessages))。
- **コメント/チャットメッセージの固定は API 非対応。**
  コメント系 API は insert / update / setModerationStatus のみ
  ([リファレンス](https://developers.google.com/youtube/v3/docs/comments/insert))。
- 上記 2 点より、**実装はブラウザ上の DOM 操作が前提**になる(→ plan.md)。
- ライブリダイレクトを「送る」側には登録者 1,000 人以上の要件があるが、
  **受け取る側の本機能に登録者要件は無い**。
- 受け取り側には「どのチャンネルからリダイレクトされるか」の許可設定があり、
  既定は「登録しているチャンネル」。テストのしやすさに影響する。

## メモ / 降りる箇所

- ~~**D1: 投稿先**~~ → **確定(2026-08-05): ライブチャット。** アーカイブのコメント欄は対象外。
- ~~**D2: 既存の固定メッセージの扱い**~~ → **確定(2026-08-05): 設定で指定できるようにする(AC8)。**
  YouTube の固定は 1 件のみで、上書きすると既存の固定(告知等)が消えるため、挙動を配信者が選ぶ。
  既定は `ifEmpty`(既存の固定があるときは投稿だけして固定はしない)。
  > ⚠️ `ifEmpty` は「**現在何かが固定されているか**」を DOM から判定できることが前提。
  > 判定手段が見つからなければ `off` / `always` の 2 値に縮退する(T1 で確認)。
- **D3: 自動投稿の是非。**
  ブラウザ自動化による自動投稿が YouTube の自動化ポリシーに触れないか、
  投稿頻度・内容の観点で判断が要る。リダイレクト受信時のみ・低頻度・人間可読の返礼文であれば
  実質リスクは低いと見るが、**判断は人間が行う**。
  → **調査済み (2026-08-06): [docs/d3-automation-policy.md](../../docs/d3-automation-policy.md)。判断は未了。**
  要点: 規約の「自動化された手段でのアクセス」に文言上は当たりうるが、
  **チャットへの投稿自体は公式 API で認められており (Nightbot 等が利用)、争点は行為ではなく経路**。
  固定には API が無く経路の選択肢がない。**ストアに出す = リスクを配布先の他人に負わせる**という点が
  判断の重心。取りうる形は A(現状) / B(自動を既定 OFF・手動を既定) / C(投稿だけ公式 API)。
- **D4: 技術スタック**(Chrome 拡張 / ユーザースクリプト / Playwright)→ plan.md で提案、要承認。
