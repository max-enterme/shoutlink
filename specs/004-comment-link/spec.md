# 004 登録した人のコメントに反応してリンクを投稿

> spec.md — フィーチャーの「何を・なぜ」。正本はこのテキストと GitHub(Feature issue)。

## 目的

**リダイレクトの受信だけでなく、「登録した人がチャットにコメントした」ことでも**
その人のチャンネル URL を含むメッセージを投稿できるようにする。

## 背景 / 課題

現状、**自動の引き金はリダイレクト受信通知の 1 種類だけ**([detector.ts](../../src/detector.ts))。
ほかにあるのは人が押す手動トリガー([manual-trigger.ts](../../src/manual-trigger.ts)・既定 OFF)で、
これも「リダイレクトを受けた」ことを人が代わりに告げる経路でしかない。

しかし配信中に紹介したい相手が来る経路はリダイレクトだけではなく、
**普通にコメントで顔を出す**ほうがむしろ多い。
そのときの「◯◯さん来てくれた、チャンネルはこちら」は、今は完全に手作業になる。

一方で、**人ごとの器はすでにある。** 呼び名の辞書
([directory.ts](../../src/directory.ts))は正規化済みチャンネル URL を鍵に持ち、
リダイレクトを受けた相手は自動で載る。**「誰に反応するか」の名簿として流用できる。**

### ⚠️ この feature の成立条件は「コメントから投稿者を特定できること」

辞書の鍵は**正規化済みチャンネル URL** で、dedupe・post-log・self-echo もすべて同じ鍵に
揃えてある。ところが **チャットのコメント要素から投稿者のチャンネル URL を取れるかは未確認**
であり、そもそも [poster.ts](../../src/poster.ts) は
「自分のチャンネルを DOM から特定する手段が未確認」という理由で、投稿したメッセージの
特定を**本文一致だけ**でやっている。確かめるべきことは 3 つある。

1. **投稿者のチャンネルが取れるか。** 取れなければ残るのは表示名の一致だけで、
   **同名の別人のコメントに反応して「◯◯さんが来てくれた」と別人のリンクを貼る**事故になる
2. **取れたとして、辞書と同じ正規形か。** `normalizeChannelUrl` は `/@handle` と
   `/channel/UC…` を**別の鍵**に正規化する([detector.ts](../../src/detector.ts))。
   辞書に載っている鍵は実配信の観測では `@ハンドル` 側([t1-findings.md](../../docs/t1-findings.md))で、
   手動登録の入力欄も `@handle` を受ける。**コメント側が `UC…` 形なら照合は永久に空振りし、
   機能が無言で 1 度も動かない**
3. **自分(拡張)の投稿を見分けられるか。** コメント返しの投稿は**それ自体がチャットコメント**で、
   検知対象と同じ種類のノードになる。しかも辞書には**配信者自身のチャンネルが載りうる**
   (`rememberSource` は投稿の可否に関わらず載せ、2026-08-05 には実際に自分のチャンネルを
   送信元として拾っている)

本 repo は送信元の取り違えを**実際に 2 回起こしている**([t1-findings.md](../../docs/t1-findings.md))。
したがって **「まず実 DOM で 3 点を採取し、その結果で照合方式を確定する」**という順序を、
tasks の並びとして固定する(T1 → 以降)。取れなかったときにどう降りるかは人間が決める(D1 / D2)。

## スコープ

- **含む**:
  - 設定 `commentReplyEnabled`(**既定 OFF**)と、コメント返し専用のテンプレート `commentTemplate`
  - `DirectoryEntry` に **「コメントに反応する」フラグ**を追加(既定 false / 自動登録時も false)
  - `DirectoryEntry` に **コメント返し専用の自由文**を追加(003 の自由文とは**別のフィールド** / D4 の決定)。
    `commentTemplate` の `{msg}` に差し込む
  - チャットのコメントから投稿者を特定する手段の**実 DOM 採取**と、それに基づく照合の確定
  - 一致したときの投稿(**固定はしない**)と、多重投稿の抑止(同一配信・同一人物に 1 回)
  - 設定画面: 有効化スイッチ、コメント用テンプレート欄とプレビュー、辞書テーブルのフラグ列、
    投稿履歴の種別表示
  - 自動投稿の範囲が広がることのドキュメント反映(README / install.md / 公開ページ / テスター資料)
- **含まない**:
  - **コメント返しの固定(ピン留め)**。固定枠は 1 件しかなく、コメントのたびに上書きすると
    リダイレクト返礼の固定が流れる。`pinMode` は**見ない**(2026-08-12 に人間が決定)
  - **リダイレクト返礼のテンプレートの流用**。文面は別に持つ(同上)
  - **辞書に載っていない人への反応**(初見の視聴者を自動で紹介することはしない)
  - **スーパーチャット・メンバー加入・キーワードなど、通常のコメント以外の引き金**(AC3)
  - **投稿者の特定手段としてメッセージのメニュー(︙ → チャンネルへ)を開くこと**。
    Polymer のメニューは合成タップと 4 秒程度の待ちが要り([pinner.ts](../../src/pinner.ts))、
    コメントごとに開くのは現実的でない
  - **003 の自由文(`DirectoryEntry.message`)をコメント用テンプレートで使うこと。**
    コメント返しには**別フィールドの自由文**を持たせる(D4 の決定 / 2026-08-13)
  - **辞書の保存先の変更**。`sync` → `local` の移行は [003](../003-per-source-message/spec.md) の
    T1 が持つ(security-review S7)。004 では触らない

## ユーザーストーリー

1. 配信者が、設定の辞書で「コメントに反応する」を @A に付けておく
2. 配信中、@A がチャットに「こんばんは」と書く
3. 数秒以内に、自分のライブチャットへ
   `Aさん、来てくれてありがとうございます! https://www.youtube.com/@A` が投稿される(固定はしない)
4. 同じ配信の中で @A が何度コメントしても、投稿は最初の 1 回だけ

## 受け入れ条件

| # | 条件 |
|---|---|
| AC1 | 設定 `commentReplyEnabled` が **既定 OFF**。OFF の間はコメントを見て何もしない(検知そのものを走らせない) |
| AC2 | 反応するのは、辞書のエントリで**「コメントに反応する」が ON の人だけ**。フラグは**既定 false**で、リダイレクト受信による自動登録でも false のまま |
| AC3 | 対象とするのは**通常のテキストコメントだけ**(`yt-live-chat-text-message-renderer` 相当)。**スーパーチャット・メンバー加入・システムメッセージ・削除済みメッセージのプレースホルダには反応しない。**既存の `SELECTORS.chatTextMessage`(スパチャとメンバー加入を含む)を**そのまま流用しない** |
| AC4 | **投稿者が辞書の鍵と同じ正規形(`normalizeChannelUrl` の出力)で一致したコメントだけ**を対象にする。特定できない / 正規形が違って一致しないコメントは**何もしない**(表示名だけの一致では投稿しない)。この条件を緩めるかどうかは D1 の決定に従い、**採る場合はこの AC を書き換えてから実装する** |
| AC5 | 投稿文は**コメント用テンプレート** `commentTemplate` から作る(既定 `{name}さん、来てくれてありがとうございます! {url}`)。`{name}` は**辞書の呼び名 → 無ければ辞書の URL から作ったハンドル**、`{url}` は**辞書に登録されている URL**。**コメント側の表示名は投稿文に使わない**(第三者が自由に決める文字列を配信者名義の投稿に載せない / security-review S3)。`{msg}` は AC16 の**コメント返し専用の自由文**。上限 200 字の扱い(削り順・コードポイント単位の切り出し)はリダイレクト返礼と同じ規則 |
| AC6 | **投稿するだけで、固定はしない。** `pinMode` の値に関わらず固定操作を行わない |
| AC7 | **同一配信・同一人物へのコメント返しは 1 回まで。**チャットの再読み込みをまたいでも抑止する(投稿履歴に残す)。配信が変われば再び 1 回投稿してよい。**配信 ID が取れないとき**(`currentStreamId()` が空)は同一配信かを判定できないため、**リダイレクト側と同じ 6 時間の下限**(`UNKNOWN_STREAM_MIN_COOLDOWN_SEC`)を保存済み履歴に対して適用する。**この下限は `cooldownSec` から独立**で、`cooldownSec = 0`(テスターに指示している値)でも外れない(`self-echo` と同じ扱い) |
| AC8 | **リダイレクト返礼とコメント返しの抑止は非対称:**<br>・同じ配信でその人へ**リダイレクト返礼を投稿済み**なら、コメント返しは**しない**<br>・同じ配信でその人へ**コメント返しを投稿済み**でも、**リダイレクト返礼は投稿する**(こちらが本命)<br>そのため**リダイレクト側の `dedupe` に渡す履歴からコメント返しの記録を除く。**既存の履歴(種別を持たない)は**リダイレクト返礼として**読む |
| AC9 | **起動時、および配信中にスイッチを ON にした時点で既にあるコメントには反応しない。**反応するのはその後に新しく現れたコメントだけ。**判定は「DOM に追加されたか」だけに頼らない** — チャット項目リストの再構築(ポップアウトの開き直し・フィルタ切替・仮想スクロールでの再挿入)で既存コメントが追加ノードとして流れるため、**メッセージのタイムスタンプ**(T1 で採取できた場合)か、**取れない場合は監視開始(= observer を張った時刻)から 10 秒の猶予**(その間に現れたコメントには投稿しない)で切る。**猶予は起動直後しか塞げない暫定手段で、猶予明けのフィルタ切替・仮想スクロールによる再挿入は素通りする。**タイムスタンプが採れなかった場合に残る歯止めは AC7(1 人 1 回)だけになり、**その状態で出すかは D2 の判断に含める** |
| AC10 | **自分(拡張・配信者)の投稿には反応しない。**(a) 投稿した要素、(b) 投稿本文と一致するコメント、(c) **配信者自身のチャンネル**(T1 で判別手段が採れた場合)のいずれでも弾く。コメント返し・リダイレクト返礼のどちらの投稿に対しても、それを引き金に再投稿しない |
| AC11 | 該当者が同時に複数現れても、投稿は**順に、最低 5 秒の間隔**を空けて行う。**1 配信あたりの「コメント返し」の上限は 20 件**(設定ではなく定数。リダイレクト返礼は数に入れない)。**数えるのは投稿履歴の「今の配信 かつ `kind='comment'`」の件数**で、リロードでリセットしない。超えたら投稿せずログに残す。**スイッチが OFF になった時点で未処理のキューは捨てる** |
| AC12 | コメント検知・照合・投稿のいずれが失敗しても**配信に影響しない**(例外を握ってログのみ / 001 AC6 と同じ) |
| AC13 | 設定画面で、有効化スイッチ・コメント用テンプレート(プレビュー付き)・辞書テーブルの**「コメントに反応する」フラグ列とコメント返し用の自由文列**が編集できる。**フラグ列・自由文列はどちらも行の編集で即保存**(既存の呼び名と同じ)、**テンプレートとスイッチは「保存」ボタン**(既存の設定と同じ)。<br>**辞書テーブルは行を畳んだ表示にする** — 既定では **ハンドル / 呼び名 / 削除ボタン**(= 現状の 3 列そのまま。`lastSeenAt` は列にせず、**現状どおりハンドルセルの `unseen` クラスと `title`** で表す)だけを出し、**自由文 2 本と「コメントに反応する」フラグは行を展開したときに出す**(D4 で 1 行が持つ編集項目が 3 → 6 になるため / plan.md R9)。**削除ボタンは畳んだ状態でも押せる**こと(辞書から消す唯一の手段を展開の裏に入れない)。<br>**畳んだ状態でも「設定したのに効かない」行が分かる**こと — **`commentMessage` が入っているのに `replyToComment` が false**(書いた一文が一生使われない)と、**`message` / `commentMessage` が入っているのに対応するテンプレートに `{msg}` が無い**(下の警告と同じ判定)。**「フラグが ON で自由文が空」は正常なので印を出さない**(AC16 の既定であり、フラグを付けた直後の全行がこの状態になる)。展開状態は保存しなくてよい。<br>**003 の 200 字超のエラー(003 AC6)と残り文字数(003 AC8)は、行を展開した状態で従来どおり出す**(畳む変更でこれらを落とさない)。<br>**具体的なレイアウトは T14 のモックで確定してから実装する**(SPEC-OPS §10)。**フラグが 1 件以上 ON なのにスイッチが OFF**、または**スイッチが ON なのにフラグが 0 件**のとき、その旨を**スイッチの直下に常時表示**する(一時表示の `status` を使わない)。投稿履歴の表に**種別**の列が出る |
| AC14 | 保存内容が壊れていても `normalizeConfig` / `normalizeDirectory` / `normalizePostLog` が落ちず、既定で埋まる。**`kind` は `'comment'` に完全一致したときだけ `comment`、それ以外(欠損・enum 外・非文字列)はすべて `redirect`。**欠損は 004 以前の記録がリダイレクト返礼しかないため。壊れた値を `redirect` に倒すのは、`redirect` の記録が AC8 により**両方の投稿を止める**側だから — `comment` に倒すと**リダイレクト側の抑止からその記録が丸ごと外れ**、リロード時の再投稿(2026-08-06 ④)が戻る |
| AC15 | 既存の挙動が変わらない。**`commentReplyEnabled` が OFF のとき、投稿・固定・ログの出力が現状と同じ**(既存テストが通る) |
| AC16 | `commentTemplate` の `{msg}` に差し込まれるのは、**コメント返し専用の自由文**(`DirectoryEntry.commentMessage`)であり、**003 の `DirectoryEntry.message`(リダイレクト返礼用)ではない**(D4)。<br>既定は空。**未登録・空なら `{msg}` が消えて前後の空白が 1 つに畳まれる**(003 AC2 と同じ形)。上限・削り順・コードポイント単位の切り出し・**自由文を再展開しない**ことも 003 と同じ規則を再利用する(003 AC3 / AC4 / AC9)。<br>**逆方向も成り立つ** — リダイレクト返礼の `template` の `{msg}` に `commentMessage` は入らない。<br>正規化は 003 と同じ(欠損・非文字列は `''`、上限超は切り詰め / AC14)。<br>**設定画面での扱いも 003 と同じ規則を「ペア単位」で適用する** — **200 字超は保存せず理由を出す**(003 AC6)/ **残り文字数は `commentTemplate` を展開した投稿文全体に対する残り**(003 AC8。`template` ではない)/ **`commentTemplate` に `{msg}` が無いのに `commentMessage` が 1 件以上あるとき警告**(003 AC7)。<br>**判定は `template` × `message` と `commentTemplate` × `commentMessage` の組で行い、組を跨いで判定しない**(片方のテンプレートに `{msg}` があることで、もう片方の警告が消えてはいけない) |

## メモ / 降りる箇所

- **D1: 投稿者の特定手段が無かった / 鍵の形が合わなかったときにどうするか。**
  T1 の採取結果しだいで、次のどれを採るかを**人間が決める。**エージェントが
  「表示名で照合すればとりあえず動く」と判断して降りてはいけない。

  | 案 | 効く範囲 | 代償 |
  |---|---|---|
  | **(a)** 表示名の完全一致で照合する | 実用上はほぼ動く | **同名の別人・改名・なりすましで誤爆する。**「◯◯さんが来てくれた」と**別人のリンク**を貼る。辞書側に「照合用の表示名」を持たせる必要もある |
  | **(b)** 表示名 + 追加の手掛かり(アイコン URL 等)の併用 | 誤爆の確率は下がる | 手掛かり自体が未確認で、**別の推測を 1 つ増やす**。当たり外れをテストで固定できない |
  | **(c)** `UC…` ↔ `@handle` の対応付けを作る(鍵の形が違うだけの場合) | 正確さは落ちない | 対応表をどこで作るかが要る。**辞書の鍵をどちらかに寄せる移行**が発生し、003 の `local` 移行と順序が絡む |
  | **(d)** 特定できないなら**本 feature を畳む**(T1 の記録だけ残す) | 誤爆ゼロ | 機能が無くなる |

- **D2: T1 で手掛かりが採れなかったとき、歯止めを 1 枚欠いたまま出すかどうか。**
  対象は 2 つあり、**どちらも人間が決める。**

  - **自分(配信者)の投稿の判別 (AC10)** — (c) が採れないと残るのは (a) 投稿要素の記憶と
    (b) 本文一致だけ。(a) は [poster.ts](../../src/poster.ts) が要素の特定に失敗しうる以上
    単独では信用できず、**実質 (b) 1 枚**になる。自己ループは「投稿 → 検知 → 投稿」の
    無限ループになりうる経路で、security-review S1 と同型
  - **メッセージのタイムスタンプ (AC9)** — 採れないと猶予 10 秒に落ちるが、猶予は
    **起動直後しか塞げない。**フィルタ切替・仮想スクロールでの再挿入は素通りし、
    残る歯止めは AC7(1 人 1 回)だけになる

- **D3: 自動投稿の範囲が広がることの判断。**
  001 の D3 は「リダイレクト受信時のみ・低頻度」という前提で
  「グレーだが開示した上で自己責任」と決着した([d3-automation-policy.md](../../docs/d3-automation-policy.md))。
  **本 feature は引き金を増やし、投稿の頻度を上げる。**前提が変わる以上、
  **同じ結論のままでよいかは人間が決める。**既定 OFF・配信内 1 回・5 秒間隔・
  1 配信 20 件の上限は頻度を抑える設計だが、**判断そのものの代わりにはならない。**

  > **決定(2026-08-13 / 人間): 001 D3 の結論を維持する。開示した上で自己責任。**
  >
  > 理由:
  > - **配布先のリスクは増えない。** `commentReplyEnabled` は既定 OFF、辞書側の
  >   `replyToComment` も既定 false(自動登録でも false)。**何もしなければ 001 と同じ挙動**で、
  >   004 は「有効にした人だけ頻度が上がる」形になる。これは
  >   **001 本体は既定 ON のまま**(`enabled: true` / [src/config.ts](../../src/config.ts))で、001 が採ったのは
  >   [d3-automation-policy.md](../../docs/d3-automation-policy.md) の **A に開示と配布経路の限定を付けた形**だが、
  >   **004 が足す引き金には B の考え方(本人に選ばせる)を適用した** — 頻度が上がる側だけを既定 OFF にしたので、
  >   **既存の利用者が黙って頻度の高い側へ動くことはない。**
  > - **ON にしたときの頻度も、スパムポリシーが撃とうとしている像から遠いまま。**
  >   1 配信・1 人につき 1 回 / 5 秒間隔 / 1 配信 20 件の上限 / 誘導先は相手のチャンネル。
  >   「大量の、反復的な」に寄る形にはしていない。
  > - 争点は 001 のときと同じく**経路(API か DOM か)**で、引き金の数はそこを動かさない。
  >
  > **やること:** [d3-automation-policy.md](../../docs/d3-automation-policy.md) に **004 で前提が変わったことと、
  > この再判断の結果**を追記する(T11 の完了条件)。ドキュメントの開示は T10 が持つ。
  >
  > **持ち越し:** 経路を公式 API(`liveChatMessages.insert`)へ寄せる案は**引き続き未採用**。
  > 004 のスコープ外で、必要になったら別 feature として起こす。

- **D4: コメント用テンプレートで 003 の自由文 `{msg}` を使えるようにするか。**
  [003](../003-per-source-message/spec.md) は辞書に自由文を足し、返礼文へ `{msg}` で差し込む。
  同じ自由文をコメント返しにも出すと、**リダイレクトを受けたときに宛てて書いた一文が
  ただのコメントに対して出る**ことになる。使えるようにするか、別のフィールドにするかは
  **人間が決める。**(どの feature を先に main へ載せるかは実装順の話で、plan.md の依存節に置く)

  > **決定(2026-08-13 / 人間): コメント返し専用の自由文を、別フィールドとして足す。**
  >
  > - `DirectoryEntry.commentMessage`(仮称)を追加し、**`commentTemplate` の `{msg}` にはこちらが入る**。
  >   003 の `DirectoryEntry.message` は**リダイレクト返礼専用のまま**にする(→ AC16)。
  > - 差し込み・削り順・上限・再展開しないことの規則は **003 が作ったものをそのまま再利用**する。
  >   004 は**フィールドを 1 本増やして経路を分けるだけ**で、`composer.ts` の規則は新設しない。
  > - **スコープが増える。** 辞書テーブルの列が **3 → 6** になる
  >   (003 の自由文列 + 004 のフラグ列 + 004 の自由文列)。**AC13 / T9 の作業量が増える。**
  >   **行を畳む表示を 004 のスコープに入れる**(AC13 / plan.md R9)。
  >   これで「既存パターンへの列追加」からは外れるため、**SPEC-OPS §10 に従って GUI モックを併置する**
  >   — **T14 として人手タスクを起こし、T9 の実装前にレイアウトを確定させる**(下の「GUI モック」節)。
  > - **003 が先に main へ載ることが前提**(plan.md 依存節)。003 の `message` が入ってから
  >   004 が 2 本目を足す形にする。逆順で作ると `{msg}` の展開機構を 004 が先に作ることになり、
  >   003 とのコンフリクトが大きくなる。

- **`{url}` はコメントから取った URL ではなく、辞書に登録されている URL を使う。**
  照合に使った値と投稿に使う値を分けておくと、照合が甘くなったときに
  「知らない URL を貼る」形の事故にならない。`{name}` を辞書側に寄せているのも同じ理由(AC5)。
