# 004 登録した人のコメントに反応してリンクを投稿

> spec.md — フィーチャーの「何を・なぜ」。正本はこのテキストと GitHub(Feature issue)。

## 目的

**リダイレクトの受信だけでなく、「登録した人がチャットにコメントした」ことでも**
その人のチャンネル URL を含むメッセージを投稿できるようにする。

## 背景 / 課題

現状、**自動の引き金はリダイレクト受信通知の 1 種類だけ**([detector.ts](../../src/detector.ts))。
ほかにあるのは人が押す手動トリガー([manual-trigger.ts](../../src/manual-trigger.ts)・既定 OFF)で、
これも「リダイレクトを受けた」ことを人が代わりに告げる経路でしかない。

しかし配信中に紹介したい相手が来る経路はリダイレクトだけではなく、
**普通にコメントで顔を出す**ほうがむしろ多い。
そのときの「◯◯さん来てくれた、チャンネルはこちら」は、今は完全に手作業になる。

一方で、**人ごとの器はすでにある。** 呼び名の辞書
([directory.ts](../../src/directory.ts))は正規化済みチャンネル URL を鍵に持ち、
リダイレクトを受けた相手は自動で載る。**「誰に反応するか」の名簿として流用できる。**

### この feature の成立条件は「コメントから投稿者を特定できること」— **T1 で確認済み**

辞書の鍵は**正規化済みチャンネル URL** で、dedupe・post-log・self-echo もすべて同じ鍵に
揃えてある。**コメント側から何が取れるか**を確かめるまで照合方式を決められないため、
**「まず実 DOM で採取し、その結果で確定する」**順序を tasks に固定した(T1 → 以降)。

**2026-08-15 に採取完了**([docs/004-t1-collect.md](../../docs/004-t1-collect.md))。確かめた 3 点:

1. **投稿者のチャンネルは取れる。** ただしリンクやテキストではなく、
   **DOM 属性 `whole-message-clickable` の中**(パーセントデコード + base64 を 2 段解いた先)。
   実配信で全メッセージ分を正解と突き合わせ、通常のテキストメッセージは**全件一致**
2. **形は `UC…` で、辞書の鍵(`@handle`)とは一致しない。**
   `normalizeChannelUrl` は `/@handle` と `/channel/UC…` を**別の鍵**に正規化する
   ([detector.ts](../../src/detector.ts))ため、そのままでは**照合が永久に空振りする。**
   → **`channelId` を辞書に足して解決する**(AC17 / D1 ②)
3. **自分(拡張・配信者)の投稿は見分けられる。** `author-type="owner"` が DOM 属性で取れ、
   同じ `params` から**配信の持ち主の ID** も取れる(AC10)。
   辞書には**配信者自身のチャンネルが載りうる**(`rememberSource` は投稿の可否に関わらず載せ、
   2026-08-05 には実際に自分のチャンネルを送信元として拾っている)ので、この 2 枚が要る

**ハンドルはどこにも無い。**表示名は `@…` の形をしていることがあるが、
**チャンネル名は誰でも自由に決められるのでハンドルの保証がない。照合には使わない**(D1)。

本 repo は送信元の取り違えを**実際に 2 回起こしている**([t1-findings.md](../../docs/t1-findings.md))。
**推測を照合の経路に置かない**という原則は、採取が済んだ後も変わらない(AC4 の fail-closed)。

## スコープ

- **含む**:
  - 設定 `commentReplyEnabled`(**既定 OFF**)と、コメント返し専用のテンプレート `commentTemplate`
  - `DirectoryEntry` に **「コメントに反応する」フラグ**を追加(既定 false / 自動登録時も false)
  - `DirectoryEntry` に **コメント返し専用の自由文**を追加(003 の自由文とは**別のフィールド** / D4 の決定)。
    `commentTemplate` の `{msg}` に差し込む
  - チャットのコメントから投稿者を特定する手段の**実 DOM 採取**と、それに基づく照合の確定
    (**採取は完了** / [docs/004-t1-collect.md](../../docs/004-t1-collect.md))
  - `DirectoryEntry.channelId`(`UC…`)と、**`@handle` からの解決**(AC17)。
    これに伴う `host_permissions`(`https://www.youtube.com/*`)の追加。**content script は増やさない**
  - 一致したときの投稿(**固定はしない**)と、多重投稿の抑止(同一配信・同一人物に 1 回)
  - 設定画面: 有効化スイッチ、コメント用テンプレート欄とプレビュー、辞書テーブルのフラグ列、
    投稿履歴の種別表示
  - 自動投稿の範囲が広がることのドキュメント反映(README / install.md / 公開ページ / テスター資料)
- **含まない**:
  - **コメント返しの固定(ピン留め)**。固定枠は 1 件しかなく、コメントのたびに上書きすると
    リダイレクト返礼の固定が流れる。`pinMode` は**見ない**(2026-08-12 に人間が決定)
  - **リダイレクト返礼のテンプレートの流用**。文面は別に持つ(同上)
  - **辞書に載っていない人への反応**(初見の視聴者を自動で紹介することはしない)
  - **スーパーチャット・メンバー加入・キーワードなど、通常のコメント以外の引き金**(AC3)
  - **投稿者の特定手段としてメッセージのメニュー(︙ → チャンネルへ)を開くこと**。
    Polymer のメニューは合成タップと 4 秒程度の待ちが要り([pinner.ts](../../src/pinner.ts))、
    コメントごとに開くのは現実的でない
  - **003 の自由文(`DirectoryEntry.message`)をコメント用テンプレートで使うこと。**
    コメント返しには**別フィールドの自由文**を持たせる(D4 の決定 / 2026-08-13)
  - **辞書の保存先の変更**。`sync` → `local` の移行は [003](../003-per-source-message/spec.md) の
    T1 が持つ(security-review S7)。004 では触らない

## ユーザーストーリー

1. 配信者が、設定の辞書で「コメントに反応する」を @A に付けておく
2. 配信中、@A がチャットに「こんばんは」と書く
3. 数秒以内に、自分のライブチャットへ
   `Aさん、来てくれてありがとうございます! https://www.youtube.com/@A` が投稿される(固定はしない)
4. 同じ配信の中で @A が何度コメントしても、投稿は最初の 1 回だけ

## 受け入れ条件

| # | 条件 |
|---|---|
| AC1 | 設定 `commentReplyEnabled` が **既定 OFF**。OFF の間はコメントを見て何もしない(検知そのものを走らせない) |
| AC2 | 反応するのは、辞書のエントリで**「コメントに反応する」が ON の人だけ**。フラグは**既定 false**で、リダイレクト受信による自動登録でも false のまま |
| AC3 | 対象とするのは**通常のテキストコメントだけ**(`yt-live-chat-text-message-renderer` 相当)。**スーパーチャット・メンバー加入・システムメッセージ・削除済みメッセージのプレースホルダには反応しない。**既存の `SELECTORS.chatTextMessage`(スパチャとメンバー加入を含む)を**そのまま流用しない** |
| AC4 | **投稿者のチャンネル ID が、辞書エントリの `channelId` と一致したコメントだけ**を対象にする(D1 の決定 / 2026-08-15)。<br>・**投稿者の ID は DOM 属性から取る** — `whole-message-clickable` の `params` を 2 段(各段ともパーセントデコード + base64)解き、**「動画 ID とペアになっている ID」= 配信の持ち主**を特定して除外し、**残りが 1 つに絞れたときだけ**それを投稿者とする。<br>・**持ち主を特定できなかったときは「取れなかった」として何もしない。**ペアが見つからないまま「残り」を採ると、**持ち主(= 配信者自身)の ID を投稿者として採りうる。**配信者自身は辞書に載りうる(`rememberSource`)ので、その行が ON だと**視聴者の全コメントが「自分への返し」を撃つ。**<br>・**ペアの判定は構造で行う**(その ID の直後に動画 ID が続いているか)。`currentStreamId()` が空でないときは**その値と一致することも確かめる**が、**空でも判定は成立する**(空を理由に機能を止めない)。**「2 つ目を採る」のような順序頼みにはしない**<br>・**辞書側の `channelId` は解決して保存する**(AC17)。**未解決のエントリはコメント照合の対象外**<br>・**表示名は照合に使わない。**特定できない / 一致しないコメントは**何もしない**(取れなかったことは診断ログに出す) |
| AC5 | 投稿文は**コメント用テンプレート** `commentTemplate` から作る(既定 `{name}さん、来てくれてありがとうございます! {url}`)。`{name}` は**辞書の呼び名 → 無ければ辞書の URL から作ったハンドル**、`{url}` は**辞書に登録されている URL**。**コメント側の表示名は投稿文に使わない**(第三者が自由に決める文字列を配信者名義の投稿に載せない / security-review S3)。`{msg}` は AC16 の**コメント返し専用の自由文**。上限 200 字の扱い(削り順・コードポイント単位の切り出し)はリダイレクト返礼と同じ規則 |
| AC6 | **投稿するだけで、固定はしない。** `pinMode` の値に関わらず固定操作を行わない |
| AC7 | **同一配信・同一人物へのコメント返しは 1 回まで。**チャットの再読み込みをまたいでも抑止する(投稿履歴に残す)。配信が変われば再び 1 回投稿してよい。**配信 ID が取れないとき**(`currentStreamId()` が空)は同一配信かを判定できないため、**リダイレクト側と同じ 6 時間の下限**(`UNKNOWN_STREAM_MIN_COOLDOWN_SEC`)を保存済み履歴に対して適用する。**この下限は `cooldownSec` から独立**で、`cooldownSec = 0`(テスターに指示している値)でも外れない(`self-echo` と同じ扱い) |
| AC8 | **リダイレクト返礼とコメント返しの抑止は非対称:**<br>・同じ配信でその人へ**リダイレクト返礼を投稿済み**なら、コメント返しは**しない**<br>・同じ配信でその人へ**コメント返しを投稿済み**でも、**リダイレクト返礼は投稿する**(こちらが本命)<br>そのため**リダイレクト側の `dedupe` に渡す履歴からコメント返しの記録を除く。**既存の履歴(種別を持たない)は**リダイレクト返礼として**読む |
| AC9 | **起動時、および配信中にスイッチを ON にした時点で既にあるコメントには反応しない。**反応するのはその後に新しく現れたコメントだけ。**判定は「DOM に追加されたか」だけに頼らない** — チャット項目リストの再構築(ポップアウトの開き直し・フィルタ切替・仮想スクロールでの再挿入)で既存コメントが追加ノードとして流れるため、**`#timestamp` のテキスト**(実配信で `5:17 PM` 形式を確認 / T1)と、**監視開始から 10 秒の猶予**を併用して切る。<br>・**パースできたときだけ時刻として使う。**受けるのは**時計表記**(`5:17 PM` / `17:17` の 2 形)。**それ以外の文字列は「読めなかった」**とする<br>・**日付は無いので、監視開始と同じ日として比較する。**比較して**12 時間以上離れて見える値は「読めなかった」**に倒す(日付をまたいだ配信で `11:59 PM` と `12:00 AM` を取り違えないため)<br>・**読めた時刻が監視開始の分より前なら投稿しない**(**分単位なので秒では切れない**)<br>・**`#timestamp` 要素そのものが見つからないときは投稿しない**(構造が変わった = 何を見ているか分からない状態。`channelId` 側と同じく安全側に倒す)。**見つかったがテキストを読めなかったときだけ猶予で判定する**(生きているコメントを取りこぼさないため)<br>・**どちらの「読めなかった」も診断ログに出す**(無言で止めない / plan.md R12)<br>・⚠️ **残る穴**: **監視開始と同じ分のコメント**は猶予明けに再挿入されると素通りする(タイムスタンプが「監視開始の分より前」にならないため)。**その範囲で残る歯止めは AC7(1 人 1 回)と AC11(20 件)だけ**<br>・µs の絶対時刻はページ内部にあるが、**そのためにメインワールドへ注入しない**(D1 の決定) |
| AC10 | **自分(拡張・配信者)の投稿には反応しない。**(a) 投稿した要素、(b) 投稿本文と一致するコメント、(c) **配信者自身のコメント**のいずれでも弾く。コメント返し・リダイレクト返礼のどちらの投稿に対しても、それを引き金に再投稿しない。<br>**(c) の手段は 2 つあり、両方使う**(T1 で確定 / 2026-08-15):<br>・**`author-type` 属性が `owner`**(DOM 属性。追加ノードにも付くことを確認済み)<br>・**投稿者の ID が、同じ `params` から得た「配信の持ち主」の ID と一致する**(AC4 のデコード結果をそのまま使うので追加の取得が要らない。`author-type` とは独立した 2 枚目になる) |
| AC11 | 該当者が同時に複数現れても、投稿は**順に、最低 5 秒の間隔**を空けて行う。**1 配信あたりの「コメント返し」の上限は 20 件**(設定ではなく定数。リダイレクト返礼は数に入れない)。**数えるのは投稿履歴の「今の配信 かつ `kind='comment'`」の件数**で、リロードでリセットしない。超えたら投稿せずログに残す。**スイッチが OFF になった時点で未処理のキューは捨てる** |
| AC12 | コメント検知・照合・投稿のいずれが失敗しても**配信に影響しない**(例外を握ってログのみ / 001 AC6 と同じ) |
| AC13 | 設定画面で、有効化スイッチ・コメント用テンプレート(プレビュー付き)・辞書テーブルの**「コメントに反応する」フラグ列とコメント返し用の自由文列**が編集できる。**フラグ列・自由文列はどちらも行の編集で即保存**(既存の呼び名と同じ)、**テンプレートとスイッチは「保存」ボタン**(既存の設定と同じ)。<br>**辞書テーブルは行を畳んだ表示にする** — 既定では **ハンドル / 呼び名 / 削除ボタン**(= 現状の 3 列そのまま。`lastSeenAt` は列にせず、**現状どおりハンドルセルの `unseen` クラスと `title`** で表す)だけを出し、**自由文 2 本と「コメントに反応する」フラグは行を展開したときに出す**(D4 で 1 行が持つ編集項目が 3 → 6 になるため / plan.md R9)。**削除ボタンは畳んだ状態でも押せる**こと(辞書から消す唯一の手段を展開の裏に入れない)。<br>**畳んだ状態でも「設定したのに効かない」行が分かる**こと — **`commentMessage` が入っているのに `replyToComment` が false**(書いた一文が一生使われない)/ **`message` / `commentMessage` が入っているのに対応するテンプレートに `{msg}` が無い**(下の警告と同じ判定)/ **`replyToComment` が ON なのに `channelId` が空**(解決できておらず、**コメントに反応しない** / AC17)。**「フラグが ON で自由文が空」は正常なので印を出さない**(AC16 の既定であり、フラグを付けた直後の全行がこの状態になる)。展開状態は保存しなくてよい。<br>**003 の 200 字超のエラー(003 AC6)と残り文字数(003 AC8)は、行を展開した状態で従来どおり出す**(畳む変更でこれらを落とさない)。<br>**レイアウトは T14 のモックで確定済み(2026-08-16)** — **展開は左端の `▸`** /
**「効かない行」の印はアイコン(`title` に理由)+ 行の背景色** / **チャンネル ID の再試行は
「展開したときの個別」と「辞書の上のまとめて再試行」の 2 つ**(畳んだ行には置かない)/
**スイッチは「リダイレクト返礼」「コメント返し」でセクションを分け、文面テンプレートも
それぞれのセクションに入れる**(plan.md R9 に確定値)。**フラグが 1 件以上 ON なのにスイッチが OFF**、または**スイッチが ON なのにフラグが 0 件**のとき、その旨を**スイッチの直下に常時表示**する(一時表示の `status` を使わない)。投稿履歴の表に**種別**の列が出る |
| AC14 | 保存内容が壊れていても `normalizeConfig` / `normalizeDirectory` / `normalizePostLog` が落ちず、既定で埋まる。**`channelId` は `UC[\w-]{20,}` に全体一致する文字列だけを受け、それ以外(欠損・非文字列・形が違う)は空文字**(AC17。壊れた値で誰かに誤爆させない)。**この形は [detector.ts](../../src/detector.ts) の `normalizeChannelUrl` が `/channel/UC…` を受けるときと同じ**にする — 揃えないと、片方が通して片方が弾く行ができる。**`kind` は `'comment'` に完全一致したときだけ `comment`、それ以外(欠損・enum 外・非文字列)はすべて `redirect`。**欠損は 004 以前の記録がリダイレクト返礼しかないため。壊れた値を `redirect` に倒すのは、`redirect` の記録が AC8 により**両方の投稿を止める**側だから — `comment` に倒すと**リダイレクト側の抑止からその記録が丸ごと外れ**、リロード時の再投稿(2026-08-06 ④)が戻る |
| AC15 | 既存の挙動が変わらない。**`commentReplyEnabled` が OFF のとき、投稿・固定・ログの出力が現状と同じ**(既存テストが通る) |
| AC16 | `commentTemplate` の `{msg}` に差し込まれるのは、**コメント返し専用の自由文**(`DirectoryEntry.commentMessage`)であり、**003 の `DirectoryEntry.message`(リダイレクト返礼用)ではない**(D4)。<br>既定は空。**未登録・空なら `{msg}` が消えて前後の空白が 1 つに畳まれる**(003 AC2 と同じ形)。上限・削り順・コードポイント単位の切り出し・**自由文を再展開しない**ことも 003 と同じ規則を再利用する(003 AC3 / AC4 / AC9)。<br>**逆方向も成り立つ** — リダイレクト返礼の `template` の `{msg}` に `commentMessage` は入らない。<br>正規化は 003 と同じ(欠損・非文字列は `''`、上限超は切り詰め / AC14)。<br>**設定画面での扱いも 003 と同じ規則を「ペア単位」で適用する** — **200 字超は保存せず理由を出す**(003 AC6)/ **残り文字数は `commentTemplate` を展開した投稿文全体に対する残り**(003 AC8。`template` ではない)/ **`commentTemplate` に `{msg}` が無いのに `commentMessage` が 1 件以上あるとき警告**(003 AC7)。<br>**判定は `template` × `message` と `commentTemplate` × `commentMessage` の組で行い、組を跨いで判定しない**(片方のテンプレートに `{msg}` があることで、もう片方の警告が消えてはいけない) |
